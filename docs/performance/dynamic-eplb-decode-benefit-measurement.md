# 动态 EPLB 的 decode 收益怎么测：从一次 forward 到稳态吞吐

测动态 EPLB 时，容易遇到一个难解释的结果：专家路由已经更均匀，decode 耗时却几乎没降。接着把更新间隔从 1000 改成 4000，或者提高并发，可能又花掉一轮模型加载和预热，仍然不知道限制收益的是什么。

我们在 DeepSeek-V4-Flash、Ascend 910C 上得到过几组差别很大的结果。普通 decode 固定实际 batch=80，更新布局后 forward 耗时只缩短约 0.65%；另一组 DSpark 诊断使用实际 batch=256，三轮 target verify 耗时缩短了 7.53%～8.61%。最后用 AISBench 比较 P、D 同时开启 EPLB 的整套部署，稳态输出吞吐提高了 4.72%。

解释这些差别，先要看每组测试计时到哪里。前两组固定一次计算，检查专家布局的作用；AISBench 覆盖持续统计、周期迁移、投机解码和 PD 供给，最后由客户端记录请求指标。局部计算少花的时间能换来多少服务吞吐，需要另外测。

## 一、先决定要证明哪一层收益

这次实验按测量范围逐步扩大：先固定同一份计算，确认新布局能否减少耗时；再加入周期更新，检查计算节省的时间能否抵消搬运；最后撤掉诊断代码，用干净的 OFF/ON 服务比较请求指标。

| 实验 | 保持什么一致 | 主要观察 |
| --- | --- | --- |
| 固定状态 A→B→A | 输入、batch、上下文、KV、图路径 | 布局改变后的普通 forward 或 target verify 耗时 |
| 周期策略 | 初始布局、负载、统计方式 | 普通计算收益、真实 update 成本、延迟尖峰 |
| 干净 OFF/ON | 模型、硬件、容量、负载和客户端 | 稳态输出吞吐、TTFT、TPOT、ITL、E2E、失败数 |

固定状态实验中的 A 指原布局。A、B 通常都保留路由统计，只冻结周期迁移，再显式触发一次更新，这样才能隔离布局变化。因此，这组实验没有测到开启统计相对完全不统计的额外开销。

PD 分离时，还要决定测 D 端还是整套部署。要研究 D，就固定 P 的配置和布局，只切换 D；要评价整个方案，就按方案运行两端并报告组合效果。P、D 同时开启后的总吞吐变化，无法单独归给 D。

后面的结果表也按这个范围命名。特别是启用 DSpark 后，target verify、完整投机迭代和客户端 TPOT 各有计时边界，写成同一个“decode 一步”会掩盖差别。

## 二、固定一次真实计算，再做 A→update→B→restore A

直接比较在线更新前后两段 forward，batch、上下文长度和请求组成可能都变了。后半段即使更快，也无法据此判断布局贡献了多少。

为控制这些变量，我们从真实负载中保存一份代表性状态。先用独立流量积累有效路由统计、生成候选布局，再固定评估输入：token、positions、seq_lens、KV 槽位及其内容，以及图档位。DSpark 还需固定这次 verify 的候选 token 和宽度。

计时顺序如下，最后恢复原布局再测一段：

```mermaid
flowchart LR
    A[原布局 A：预热与计时] --> U[一次真实 update]
    U --> B[新布局 B：相同状态计时]
    B --> R[恢复布局 A]
    R --> C[相同状态再次计时]
```

一次重放也会写入 KV，所以复用同一批输入对象并不能保证状态相同。观察器需要让每次执行读取等价的 KV 状态，并核对输入指纹、逻辑专家选择和输出数值。布局更新后，已捕获的图仍应读到原权重地址；恢复 A 后，物理路由计数也应回到原分布。诊断重放要排除在学习窗口之外，否则同一份输入会反复参与布局规划。

NPU Event 包住实际 eager 执行或图回放。每次重放先取 16 个 rank 中最大的 Event 跨度，再对同一块的样本求中位数。这里要观察的是慢端造成的等待：把 16 份时间相加会重复计算并行工作，只看 rank 0 又可能漏掉最慢的设备。

首步单独报告，排除规则在测试前确定。普通 decode 每块重放 20 次，首步单列，其余 19 次取中位数。后续 DSpark 实验每块先预热 3 次，再测 30 次；第一个测量样本单列，对余下 29 次汇总。原始值全部保留，profile trace 另外采短窗口。

恢复 A 是为了检查顺序漂移。设备频率、温度和缓存状态都可能随时间变化，让后测的一段更快或更慢。如果恢复后的 A 也快了同样幅度，就需要重新判断 B 的收益。另外，相同状态的多次重放属于相关样本；要覆盖业务分布，还需在不同请求和上下文上重复。

## 三、batch 要读实际值，均衡度要和时间一起看

客户端并发设为 256 时，D 端每轮未必有 256 个请求可执行。P 端供给、PD 传输、请求到达和 KV 准入都会影响实际 batch。在 attention DP16 配置下，还需要分别记录每个 rank 的请求数和图桶大小。

我们有一组普通 decode 实验，客户端并发为 256，保存评估状态时的全局实际 batch 为 240。每个 rank 有 14～16 个请求，却都使用大小为 16 的图桶，全局共分配了 256 个图槽。这组结果应按实际 batch 报告；写成 batch=256，会把图容量算成真实负载。

| 普通 decode 固定批次 | 原布局 A | 更新布局 B | 恢复 A | B 相对首次 A |
| --- | ---: | ---: | ---: | ---: |
| 实际 batch=80，ms | 39.727 | 39.468 | 39.843 | -0.65% |
| 实际 batch=240，ms | 43.794 | 43.004 | 43.902 | -1.80% |

表中每一行都在各自的 A/B/A 内固定了状态，两行之间并非只改变 batch，因而不能用来做严格的缩放比较。它们说明了为什么要在代表性负载上实测：一个小 batch 的结果不足以覆盖其他 decode 场景。

耗时之外，我们还核对了有效路由。batch=80 那次，43 层的平均 rank 负载均值/max 从 43.86% 提升到 59.28%，其中 40 层最忙 rank 的路由数下降。但对应的 forward 只快约 0.65%。

短 trace 提供了一些解释线索。采样 rank 的稳定图主体约 37.5 ms，其中 Attention 子层约 19 ms，专家 GMM 累计约 4 ms；更新前后，整条 routed 路径没有明显缩短。路由数变得均匀，未能等比例减少关键路径耗时。还需要考虑图桶、活跃专家、分组矩阵乘、权重读取和通信等待的影响。

上述时间区间存在包含和重叠，不能相加成整步耗时。接收计数也需区分 padding 与有效路由，具体见[DeepEP 有效路由一文](deepep-received-vs-valid-routes.md)。更新前已很均衡的样本同样要保留：这些负载留给布局调整的空间本来就小，筛掉它们会夸大收益。

## 四、DSpark 先测 verify，再补完整迭代的分母

DSpark 改变了 target 每轮的计算量。在 gamma5、verify width6 的配置下，全局 256 个请求可对应 1536 行 target verify；每个 rank 的 16 个请求对应 96 行。普通 decode 每个请求只处理一个新 token，两者的计算形态已有差别。

积累真实连续满批的路由统计后，我们做了三轮固定 A/B/A。表中只计 target verify；每轮内，候选、位置和 KV 状态保持一致：

| 实际请求 batch=256 | A，ms | B，ms | 恢复 A，ms | B 耗时减少 |
| --- | ---: | ---: | ---: | ---: |
| 第 1 轮 | 87.214 | 79.706 | 86.021 | 8.61% |
| 第 2 轮 | 87.695 | 81.091 | 86.014 | 7.53% |
| 第 3 轮 | 86.766 | 79.985 | 87.394 | 7.82% |

第一轮路由均衡度从约 0.453 提升到 0.765。三轮中，B 都比前后两段 A 更快；恢复 A 的漂移也保留在表中。这支持了一个具体结论：在这组计算形态下，调整专家布局能减少 target verify 耗时。

不过，完整投机迭代还要执行 draft、验证后的接受与提交，以及调度。每轮真正提交的输出 token 数也可能变化，因而还需结合 AL 和严格接受率看结果。该实验另外保留了以下原生计数窗口：

| 负载点 | AL，含 bonus | 接受的 draft / 实际 verify 候选槽 | 严格接受率 | gamma / verify |
| --- | ---: | ---: | ---: | --- |
| C128 | 5.5352 | 19,633 / 21,645 | 90.70% | 5 / 6 |
| C256 | 5.2242 | 17,746 / 21,005 | 84.48% | 5 / 6 |

表中计数合并自各 DP rank 末尾的原生记录窗口，包含排空过程。AL 使用请求结束截断之前的提交长度。这些窗口与三轮 A/B 计时没有逐一对应，也不同于最终 AIS 稳态窗口；它们可以描述这批负载的投机行为，却不能用来把 batch 差异归因给 EPLB。

这里的严格接受率使用实际接受前缀和实际候选槽计数。只有 AL 时，`(AL-1)/gamma` 仍不能替代实测严格接受率。评价完整迭代，要比较同一窗口的总输出与总耗时；target verify 快了 8%，并不说明未计时的 draft 和提交部分也快了 8%。

## 五、先问搬运能否回本，再调 I 和 W

确认布局能减少一次计算的耗时后，就可以估算周期 update 是否划算。简化预算为：

```text
每步净节省 ≈ 普通计算的节省
           − 一次更新带来的额外时间 / 更新间隔
           − 相对真正 OFF 新增的持续统计开销
```

使用这个预算，需要假设布局收益在更新间隔内持续，并让计算收益与更新成本采用同一种迭代单位。DSpark 的一次 target verify 和一个最终输出 token 不可互换，更新间隔 I 的单位也不是毫秒。

以 batch=240 的诊断为例：每步约省 0.790 ms，第一次完整 update 在最慢 rank 上的墙钟约 1535 ms。假设收益持续，约需 1943 步才能抵消这次首次更新。这个估算有明确限制：首次 update 包含首次 dump 路径，恢复 A 的迁移又没有执行完整重平衡规划，两者都不能当作稳定热态 update 的成本。

采集更新成本时，同时保留整次更新的墙钟和各阶段设备时间。load 执行 NZ→ND；迁移包含 P2P、等待和本地拷贝；store 执行 ND→NZ 与写回。CPU 提交 send/recv 所花的几毫秒，只覆盖提交过程。设备阶段使用 Event 计时并延后读取，避免逐段插入全设备同步，改变原本的执行过程。

计算“转换占 forward 百分比”时，先在每个 rank 内，将同一窗口的阶段累计时间与正常 forward 累计时间配对，再汇总结果。16 份阶段时间不能除以一份 forward；相互重叠的区间也不能直接相加成阻塞比例。内置 update 日志的起止点仍需核对，而更新最终怎样影响服务，要由客户端指标确认。

I 决定多久检查一次更新，W 决定规划使用多少条记录。该版本在正窗口配置下要求 W≤I。可以先固定 W1000，对比 I1000/I4000，再固定 I4000，对比 W1000/W4000，减少长测组合。这里还要区分记录窗口与统计开关：缩小 W，并不会让统计只在最后 W 步开启。

一组已有的 non-spec 策略诊断从学到的布局 B 出发。冻结布局时，热尾段吞吐为 5608.78 token/s；I4000/W1000 和 I4000/W4000 分别为 5556.02、5566.06。持续更新没有显示出额外收益。这组数据来自单次顺序诊断，统计始终开启，不能标成干净 OFF。就这次观察而言，拉长间隔可以减少搬运频率，但没有解决布局本身收益有限的问题。

比较策略前，还要确认统计窗口是否由 target 记录推进。draft 空记录会挤占 W，改变窗口覆盖的有效历史，见[零记录与窗口覆盖](eplb-zero-record-rolling-window.md)。窗口含义变了，即使参数相同，也已不是同一组策略条件。

## 六、稳态 OFF/ON 要把容量、预热和窗口一起对齐

固定计算测到收益后，撤掉诊断 hook，再做完整服务比较。两组需对齐模型、代码、设备数、并行方式、冗余专家与初始布局、DSpark 配置、实际 KV 容量，以及输入输出、采样、缓存、并发、速率和客户端计时。

内存预算比例设成相同值，仍可能得到不同的 KV 容量，因为 EPLB 的额外资源会影响自动分配。应以实际启动记录为准。提高并发时，先按本地序列数、完整上下文和页对齐核算容量，再单独检查图捕获档位能否覆盖目标 batch。

预热需要经过模型、图和本次要测的迁移路径。我们的 PD/MF 环境重启后先跑两轮短测，再做长预热，并确认 ON 已实际触发更新。这是该环境的处理经验，其他服务不必照搬短测轮数。若负载仍在运行、服务也健康，采集失败后应先修复原数据，减少重复加载模型的成本。

稳态区间按工具实现选择。该次 AISBench 3.1.0 的 `StablePerfMetricCalculator` 从第二次达到最大并发的时刻开始，到最后一次达到该并发的时刻结束，再纳入 start_time 位于区间内的请求；可对照[固定版本源码](https://github.com/AISBench/benchmark/blob/e00d1f758310c45580576af291a3126919776c89/ais_bench/benchmark/calculators/stable_perf_metric_calculator.py)。总请求数需要支撑这样的区间，只发一批与并发数相同的请求，往往无法形成所需稳态。

正式配对使用 `f6ad2f4f`。P、D 各运行 16 个 Ascend 910C 逻辑设备，配置为 TP16/EP16/attention DP16，两端各有 16 个冗余专家，DSpark 为 5/6。ON 使用 P I50/W50、D I4000/W1000；两组实际 KV 上限均为 P369024、D524288。负载为合成复制任务，输入 16,388 token、固定输出 12,288 token，共 1536 请求，闭环并发 256，关闭前缀缓存。

| AIS 原生稳态指标 | OFF | ON |
| --- | ---: | ---: |
| 正式成功 / 失败 | 1536 / 0 | 1536 / 0 |
| 稳态样本 / 区间时长 | 1280 / 1075.76 s | 1280 / 1027.27 s |
| 输出吞吐，token/s | 14,620.99 | 15,311.06 |
| 平均 TTFT，s | 15.80 | 13.45 |
| 平均 TPOT，ms | 16.57 | 15.96 |
| 平均 ITL，ms | 95.68 | 92.09 |
| 平均 E2E，s | 219.46 | 209.59 |
| AL 原生 gauge，采样均值 | 5.7666 | 5.7512 |
| 严格全局 draft 接受率 | NOT_OBSERVED | NOT_OBSERVED |

这次配对的输出吞吐增加 4.72%，平均 TPOT 减少 3.69%，结果已经包含迁移对服务的影响。由于两端同时开启 EPLB，收益应归于组合方案。稳态区间内，D 更新了 3 次，P 更新了 11 次；原生日志中，每轮最慢 rank 的耗时均值分别约为 714 ms 和 680 ms。

这张表的接受率与前一节采用不同口径。这里没有实际 proposed token 分母，只有原生 accept-rate gauge：OFF/ON 采样均值为 95.33%/95.02%，范围为 78.53%～100%/80.09%～100%；AL 范围为 4.9266～6/5.0047～6。这些 rank/time 未加权采样无法给出全局严格接受率。

平均值改善的同时，长尾变差了：P99 TTFT 从 45.96 s 升到 53.05 s，P99 TPOT 从 22.88 ms 升到 23.96 ms，P99 E2E 从 299.85 s 升到 314.34 s。这些代价需要与吞吐收益一起报告。TTFT 本身还包含排队、prefill 和 PD 交接，不能用它代替一次 prefill forward 的耗时。

## 七、下一轮实验，用上一层的结果决定

下一轮测什么，取决于当前卡在哪一步。固定状态下没有收益，先检查实际 batch、有效路由和 MoE 关键路径；调整 I 可以减少搬运次数，却解释不了这次计算为什么没变快。固定 forward 已有收益，再根据热态 update 成本与负载漂移选择更新周期，最后用干净的稳态配对验证服务表现。

若要拆出 D 的独立贡献，就固定 P，比较 D OFF/ON。若要确认整套部署是否值得保留，就重复完整配对，记录每轮结果及返回基线后的变化。短 trace 的局部百分比不能替代整服务结果，不利的负载点也应保留到正式报告中。

读者复核时，需要能将以下记录对应起来：A/B/A 的固定输入和 Event 样本、更新前后的有效路由、更新边界及阶段时间、同一窗口的接受计数、实际 batch/context 分布，以及原生客户端结果和终端输出。有这些对应关系，才能查到收益在哪段计算产生，又被哪些开销抵消。

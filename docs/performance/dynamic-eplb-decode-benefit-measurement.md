# 动态 EPLB 的 decode 收益怎么测：从一次 forward 到稳态吞吐

动态 EPLB 更新了专家布局，路由也更均匀了，decode 却几乎没变快。这时继续把更新间隔从 1000 调到 4000，或者再加并发，很容易花掉一轮模型加载和预热，最后仍然解释不清结果。

我们在 DeepSeek-V4-Flash、Ascend 910C 上遇到过这个过程。固定真实 batch=80 的普通 decode，更新后 forward 只缩短约 0.65%；换到 DSpark、实际 batch=256 的另一组诊断，target verify 三轮缩短了 7.53%～8.61%；最终 P、D 同时开启 EPLB 的 AISBench 配对中，稳态输出吞吐提升 4.72%。

这些数字各自成立，回答的问题却不同。前两个测专家布局对一次计算的影响，最后一个把持续统计、周期迁移、投机解码、PD 供给和客户端计时放在一起。测 decode 收益，需要把这条链路一段段接起来。

## 一、先决定要证明哪一层收益

我会先把实验分成三层。第一层很短，确认新的布局有没有让同一份计算更快；第二层加入周期更新，判断搬运能否回本；第三层才使用干净 OFF/ON 服务比较请求指标。

| 实验 | 保持什么一致 | 主要观察 |
| --- | --- | --- |
| 固定状态 A→B→A | 输入、batch、上下文、KV、图路径 | 布局改变后的普通 forward 或 target verify 耗时 |
| 周期策略 | 初始布局、负载、统计方式 | 普通计算收益、真实 update 成本、延迟尖峰 |
| 干净 OFF/ON | 模型、硬件、容量、负载和客户端 | 稳态输出吞吐、TTFT、TPOT、ITL、E2E、失败数 |

第一层里的 A 是原布局，不是 EPLB 完全关闭。为隔离布局变量，A、B 的统计通常都开着，只冻结周期迁移，再显式触发一次更新。它测不出“开启统计比完全不统计多付多少”。

PD 分离还多一个归因问题。想研究 D 本身，可以固定 P 的配置和布局，只切换 D；想评价整个部署，就让两端按方案运行，报告组合效果。P、D 一起开启后的总吞吐变化，不能单独归给 D。

这一步分清楚，后面的每张表才能有合适的名字。尤其是开启 DSpark 后，target verify、完整投机迭代和客户端 TPOT，不能再统称为“decode 一步”。

## 二、固定一次真实计算，再做 A→update→B→restore A

比较更新前后的连续两段在线 forward，往往同时改变了 batch、上下文长度和请求组成。即使更新后快了，也很难确认是布局的作用。

我们的做法是在真实负载中保存一份代表性状态。先用独立流量积累有效路由统计，得到候选布局；再固定评估用的输入 token、positions、seq_lens、KV 槽位及内容、图档位。DSpark 还要固定这次 verify 的候选 token 和宽度。

随后执行：

```mermaid
flowchart LR
    A[原布局 A：预热与计时] --> U[一次真实 update]
    U --> B[新布局 B：相同状态计时]
    B --> R[恢复布局 A]
    R --> C[相同状态再次计时]
```

重放本身也会写 KV，因此“输入对象没换”还不够。观察器必须让每次执行看到等价的 KV 状态，并校验输入指纹、逻辑专家选择和输出数值。更新后原权重地址仍要可供已捕获的图读取；恢复 A 后，物理路由计数应恢复到原来的分布。诊断重放也不能再进入学习窗口，否则会用同一份输入反复训练布局。

计时用 NPU Event，包住实际 eager 或图回放路径。每次先取 16 个 rank 的最大 Event 跨度，再在同一块的重放样本中求中位数。不要把 16 个 rank 的耗时相加，也不要只挑 rank 0。并行计算的慢端更接近我们要解释的等待。

首步要单列，排除规则在测试前确定。普通 decode 的诊断每块重放 20 次，首步单列，其余 19 次取中位数；DSpark 的后续实验每块先预热 3 次，再测 30 次，单列第一个测量样本，对剩余 29 次汇总。所有原始值保留，profile trace 另采短窗口。

恢复 A 用来检查顺序漂移。例如设备频率、温度、缓存状态随时间变化，可能让第二段天然更快或更慢。如果 A 返回后也快了同样幅度，B 的收益就需要重新解释。相同状态的多次重放是相关样本；跨不同请求和上下文的重复，才逐步接近业务分布。

## 三、batch 要读实际值，均衡度要和时间一起看

客户端并发 256，不等于 D 每轮真的执行 256 个请求。P 的供给、PD 传输、请求到达和 KV 准入都会改变实际 batch。attention DP16 下，还要记录每 rank 的真实请求数和图桶大小。

一组普通 decode 实验的客户端并发是 256，固定评估时的真实全局 batch 却是 240。每 rank 有 14～16 个请求，图桶都是 16，全局分配了 256 个图槽。报告里写 batch=256，就把图容量当成了真实负载。

| 普通 decode 固定批次 | 原布局 A | 更新布局 B | 恢复 A | B 相对首次 A |
| --- | ---: | ---: | ---: | ---: |
| 实际 batch=80，ms | 39.727 | 39.468 | 39.843 | -0.65% |
| 实际 batch=240，ms | 43.794 | 43.004 | 43.902 | -1.80% |

两行各自在 A/B/A 内固定状态，不能把它们当作只有 batch 不同的严格缩放实验。它们的价值是说明：代表性负载要实际测，单个小 batch 不能替所有 decode 场景下结论。

还要同时看更新前后的有效路由。batch=80 那次，43 层的平均 rank 负载均值/max 从 43.86% 提升到 59.28%，40 层最忙 rank 的路由数下降，但 forward 只快约 0.65%。

短 trace 给出了原因的方向：采样 rank 的稳定图主体约 37.5 ms，其中 Attention 子层约 19 ms，专家 GMM 累计约 4 ms；更新前后整条 routed 路径没有明显缩短。路由数更均匀，并没有等比例转化成关键路径时间减少。图桶、活跃专家、分组矩阵乘、权重读取和通信等待都还在发挥作用。

这些时间区间有包含和重叠关系，不能相加成整步耗时。接收计数中的 padding 也应先与有效路由分开，具体例子见[DeepEP 有效路由一文](deepep-received-vs-valid-routes.md)。更新前已经很均衡的样本照常保留，它说明该负载本来就没有多少布局空间；不能只挑失衡最大的样本展示。

## 四、DSpark 先测 verify，再补完整迭代的分母

DSpark 会改变 target 每轮处理的计算量。gamma5、verify width6 时，全局 256 个请求对应的 target verify 行数可以达到 1536，每 rank 16 个请求、96 行。这与普通 decode 每请求处理一个新 token 的计算形态不同。

我们在真实连续满批统计后做了三轮固定 A/B/A。下面只计 target verify，候选、位置和 KV 状态在每轮内一致：

| 实际请求 batch=256 | A，ms | B，ms | 恢复 A，ms | B 耗时减少 |
| --- | ---: | ---: | ---: | ---: |
| 第 1 轮 | 87.214 | 79.706 | 86.021 | 8.61% |
| 第 2 轮 | 87.695 | 81.091 | 86.014 | 7.53% |
| 第 3 轮 | 86.766 | 79.985 | 87.394 | 7.82% |

第一轮的路由均衡度从约 0.453 提升到 0.765。三轮 B 都比前后两段 A 快，恢复 A 的漂移也保留下来。这个结果证明，该计算形态下专家布局确实能缩短 target verify。

完整投机迭代还包含 draft、验证后的接受与提交、调度等工作，每轮真正提交的输出 token 数也会变化。因此还需要 AL 和严格接受率。该实验另外保留的原生计数窗口如下：

| 负载点 | AL，含 bonus | 接受的 draft / 实际 verify 候选槽 | 严格接受率 | gamma / verify |
| --- | ---: | ---: | ---: | --- |
| C128 | 5.5352 | 19,633 / 21,645 | 90.70% | 5 / 6 |
| C256 | 5.2242 | 17,746 / 21,005 | 84.48% | 5 / 6 |

这些是各 DP rank 末尾原生记录窗口的合并，包含排空，AL 取提交长度、在请求结束截断之前；不是三轮 A/B 各自的接受率，更不是最终 AIS 稳态窗口。它们描述这批负载的投机行为，不用于把 batch 差异归因给 EPLB。

严格接受率来自实际接受前缀与实际候选槽的计数。只有 AL 时，不用 `(AL-1)/gamma` 冒充实测严格接受率。最终要比较的是同一窗口的总输出和总耗时；verify 快了 8%，其中未计时的 draft 及提交部分并不会自动也快 8%。

## 五、先问搬运能否回本，再调 I 和 W

有了单次计算的布局收益，再把 update 放回时间线。一个便于预算的简化关系是：

```text
每步净节省 ≈ 普通计算的节省
           − 一次更新带来的额外时间 / 更新间隔
           − 相对真正 OFF 新增的持续统计开销
```

它要求收益在这段时间内持续，并且更新成本与所比较的计算使用同一种迭代单位。DSpark 的一次 target verify 不是一个最终输出 token；更新间隔 I 也不是毫秒数。

用 batch=240 的诊断做条件预算：每步约省 0.790 ms，第一次完整 update 最慢 rank 的墙钟约 1535 ms。若这份收益持续，光抵消这次首次更新就需要约 1943 步。该首次成本含首次 dump 路径，恢复 A 的迁移又不含完整重平衡规划，二者都不能直接冒充稳定热态 update。

正式采集要同时保留整次更新墙钟与阶段设备时间。NZ→ND 是 load；迁移阶段包含 P2P、等待和本地拷贝；store 包含 ND→NZ 与写回。CPU 提交 send/recv 花了几毫秒，不能代替设备搬运完成时间。阶段计时用 Event，延后读取，避免为了每段读数插入全设备同步而改变执行。

若要报“转换占 forward 百分比”，先按 rank 配对同一窗口的阶段累计时间与正常 forward 累计时间，再汇总各 rank。不要把 16 份阶段耗时除以一份 forward；有重叠的区间也不能相加成阻塞比例。内置 update 日志的计时起止点同样要查清，服务端真正影响最终仍由客户端测量覆盖。

I 控制更新检查间隔，W 控制用于规划的记录窗口。在该版本的正窗口配置中要求 W≤I。可以先固定 W1000 比 I1000/I4000，再在 I4000 下比 W1000/W4000，不必把所有组合展开成长测。缩小 W 也不意味着只在最后 W 步开启统计。

已有一组 non-spec 策略诊断从学到的布局 B 出发：冻结布局的热尾段吞吐为 5608.78 token/s，I4000/W1000 为 5556.02，I4000/W4000 为 5566.06。持续更新没有比冻结 B 显示额外收益。这是单次顺序诊断，统计始终开启，不能叫干净 OFF；它足以提醒我们，拉长间隔能减少搬运频率，却不会凭空创造新的布局收益。

同时检查统计窗口是否真的由 target 记录推进。draft 空记录挤占 W 的问题，会改变有效历史，见[零记录与窗口覆盖](eplb-zero-record-rolling-window.md)。参数相同但窗口含义不同，也不能拿来作策略对照。

## 六、稳态 OFF/ON 要把容量、预热和窗口一起对齐

固定计算确认有收益之后，再换成不带诊断 hook 的干净服务。至少固定模型、代码、设备数、并行方式、冗余专家与初始布局、DSpark 配置、实际 KV 容量、输入输出、采样、缓存、并发、速率和客户端计时。

内存预算比例相同还不够。EPLB 额外资源可能影响自动分配，最终应按实际启动记录核对 KV 容量。增大并发以前，也要按本地序列数、完整上下文和页对齐检查容量；图捕获档位是否覆盖目标 batch 则是另一项约束。

预热既要覆盖模型与图，也要覆盖本次要测的迁移路径。我们的 PD/MF 环境在重启后先跑两轮短测，再做长预热，并确认 ON 已实际触发更新。两轮短测是该环境的处理经验，不是所有服务都需要照搬的常数。负载不中断、服务健康时，采集失败应先修原数据，避免为补一张表重复加载模型。

稳态使用工具明确的选择规则。该次 AISBench 3.1.0 的 `StablePerfMetricCalculator`，从第二次达到最大并发的时刻开始，到最后一次达到该并发的时刻结束，纳入 start_time 落在区间内的请求。[固定版本源码](https://github.com/AISBench/benchmark/blob/e00d1f758310c45580576af291a3126919776c89/ais_bench/benchmark/calculators/stable_perf_metric_calculator.py)中可以直接核对。请求总数要足够支撑这个区间，不能只发一批等于并发数的请求就期待得到稳态。

我们的正式配对固定 `f6ad2f4f`：P、D 各 16 个 Ascend 910C 逻辑设备，TP16/EP16/attention DP16，两端各 16 个冗余专家，DSpark5/6。ON 使用 P I50/W50、D I4000/W1000；实际 KV 上限 P369024、D524288，两组相同。合成复制任务输入 16,388、固定输出 12,288 token，1536 请求、闭环并发 256、前缀缓存关闭。

| AIS 原生稳态指标 | OFF | ON |
| --- | ---: | ---: |
| 正式成功 / 失败 | 1536 / 0 | 1536 / 0 |
| 稳态样本 / 区间时长 | 1280 / 1075.76 s | 1280 / 1027.27 s |
| 输出吞吐，token/s | 14,620.99 | 15,311.06 |
| 平均 TTFT，s | 15.80 | 13.45 |
| 平均 TPOT，ms | 16.57 | 15.96 |
| 平均 ITL，ms | 95.68 | 92.09 |
| 平均 E2E，s | 219.46 | 209.59 |
| AL 原生 gauge，采样均值 | 5.7666 | 5.7512 |
| 严格全局 draft 接受率 | NOT_OBSERVED | NOT_OBSERVED |

输出吞吐增加 4.72%，平均 TPOT 减少 3.69%。这是两端同时开 EPLB 的一次配对结果，包含了迁移对服务的实际影响。D 在稳态内更新 3 次，P 更新 11 次；原生日志每轮最慢 rank 的均值分别约 714 ms、680 ms。

接受率的口径与前一节不同：这里没有保存实际 proposed token 分母。原生 accept-rate gauge 的采样均值 OFF/ON 为 95.33%/95.02%，范围 78.53%～100%/80.09%～100%；AL 范围为 4.9266～6/5.0047～6。它们是 rank/time 未加权采样，不能改名为全局严格接受率。

平均值也要与长尾一起交付。该配对 P99 TTFT 从 45.96 s 升到 53.05 s，P99 TPOT 从 22.88 ms 升到 23.96 ms，P99 E2E 从 299.85 s 升到 314.34 s。吞吐收益和长尾代价同时存在，不能只留下正向的几行。TTFT 还含排队、prefill 和 PD 交接，不能把它当一次 prefill forward。

## 七、下一轮实验，用上一层的结果决定

固定状态下没有布局收益，就先看实际 batch、有效路由和 MoE 关键路径；反复调整 I 只能减少搬运，解释不了布局为什么没有让计算变快。固定 forward 有收益，再用热态 update 和负载漂移决定更新周期。最后的干净稳态配对，才负责确认这些局部变化能否改善服务。

如果希望证明 D 的独立贡献，下一轮把 P 固定，做 D OFF/ON；如果希望确认部署价值，就重复完整配对，保留每一轮和返回基线的变化。不要用一次短 trace 的百分比去覆盖整服务结果，也不要在正式结果之前删除不利负载点。

最后值得交付的材料，是能互相对上的一套记录：固定 A/B/A 的输入与 Event 样本、更新前后有效路由、真实更新边界与阶段时间、同一窗口的接受计数、实际 batch/context 分布、原生客户端结果和终端输出。这样，别人问“decode 到底赚在哪里”，才可以沿着证据回答到具体一步。

# Ascend 910C推理调优负例分析：为什么合理的优化没有带来吞吐收益

这轮 DeepSeek-V4-Flash、Ascend 910C 调优尝试了 CP 拓扑、Prefill 分块和通信轮次、请求速率、专家布局及 DSPARK Compact。提出时各有机制依据，测量却给出不同的取舍。

有的配置降低了 TPOT，完成吞吐却也下降；有的重新采集、拟合并加载布局，只带来约 0.81% 的变化；还有一次把到达速率提高四倍，native 几乎不变，whole 却改善了。

这些结果需要分别判断：候选是否值得保留，是否改善了另一个目标，或者这轮证据根本还没有回答原问题。如果都记成“无效”，下一次可能重复做同样试验，也可能过早丢掉仍有价值的配置。

本文使用 2026 年 10 月 18—21 日的 PD 快照和原 AISBench 统计，不外推当前上游，也未混入后续动态 EPLB。正向结果见[整体复盘](ascend-910c-inference-tuning-effective-optimizations-and-costs.md)，编排返工见[流程复盘](inference-tuning-workflow-postmortem.md)。这里主要看负例怎样改变下一步。

## 一、先分清三种不同的“没收益”

目标是 P、D 各 8 张物理卡的真实 PD，在平均 TPOT 严格低于 20ms 时提高系统输出。每卡均以 P+D 共 16 张卡归一化，C 表示客户端在途上限，N 为正式总请求，r 为配置速率。

两个场景分别为：16K 正文，Chat 包装后 16388 Token，输出 1024、零缓存；128K 正文，Chat 包装后 131076 Token，输出 1024、逐条缓存 90.6222%。普通任务与高 AL 复制展示集也分开比较。下面的正式对照均无请求失败，但没有完成通用业务精度评估。

若在当前目标下 whole、native 都下降，其他指标也不足以抵偿，可以不保留候选。这个工程决定不要求先证明普适规律：一次下降 1%，仍不能宣称它在所有环境都慢 1%。

有些候选改善的是其他方面。TPOT 下降未必缩短整轮，提高 r 可能只缩短升载。读数各有价值，需要按目标评价，不能只用某一列下结论。

还有些试验没有回答问题。请求未发出、collector 导入失败或窗口太短，都缺有效性能证据；同时修改其他配置时，也不能单独归因。这些情况应修执行或测量边界，再决定后续。

whole 包含正式升载与排空，native 按 AISBench 原算法选择统计区间。报告保留两种结果，不另删慢请求构造稳态，也不把 whole 的接受计数挪到 native。

小幅正向同样如此。D Graph 增加档位 6，在同 N480/C88/r4 中 native 约 +3.93%，whole 约 +0.51%。可以据此保留，但应同时报告，不能只摘较大值，更不能与其他负载收益相加。

## 二、减小CP、增大chunk：局部变快为何没有变成系统收益

第一组使用相同 16K 普通数据、N480/C88/r4，将 CP4/DP4 改成 CP2/DP8，并配套调整通信，D 与输入保持一致。

| native指标 | 原方案 | 候选方案 |
| --- | ---: | ---: |
| 输出吞吐(token/s/卡) | 181.20 | 179.56 |
| TTFT均值(s) | 10.57 | 12.83 |
| TPOT均值(ms) | 19.3 | 17.2 |
| E2E均值(s) | 30.29 | 30.45 |

native 约 −0.91%、whole 约 −1.64%。生成阶段的 TPOT 更低，TTFT 却增长，E2E 未缩短，因此没有获得整体完成收益。

缩小 CP 同时改变了各单元的工作量、DP 请求分布和通信形状。本组对照评价的是联合拓扑，没有隔离 CP 的单项作用，也不能从 TPOT 反推出 P 某段通信花了多久。

chunk 候选针对的是孤立尾块：输入为 16388、有效 chunk 为 8192、Prefill 请求上限为 1 时，第三块只剩 4 Token。改为 8320 可以在两块内完成，但配套通信也从 round1 切到了 round2。

同高 AL 复制任务、N320/C128/r6 的结果为：

| 指标 | 8192 / round1 | 8320 / round2 |
| --- | ---: | ---: |
| native输出(token/s/卡) | 164.88 | 163.28 |
| whole输出(token/s/卡) | 145.72 | 144.76 |
| native TPOT(ms) | 7.8 | 7.0 |

native 约下降 0.97%，whole 约下降 0.66%。候选改变了分块，吞吐却没有改善。由于缺少阶段计时，尚不能把损失归给每块多出的 128 Token 或第二轮通信；本次停止的是这套联合配置。

后来保留 8192/round1，单批请求上限从 1 调为 2，让尾块接下一条输入，同 N640 native 提高 32.27%。它处理相同尾块，却改变了不同执行条件。

于是下一步转查预算未满为何停止接纳，而非继续扫 chunk。减少分块或局部延迟只是中间结果，完成整组请求仍需系统测量。

## 三、请求速率提高四倍：容量没涨，但不能说完全没用

r 是较低成本的热参数，但它先改变提交节奏，并未直接改变设备处理速度。

相同 16K 普通任务、N320/C88、G5，将 4 req/s 改为 16 req/s：

| 指标 | 4 req/s | 16 req/s |
| --- | ---: | ---: |
| native输出(token/s/卡) | 181.5392 | 181.5425 |
| native实际完成速率(req/s) | 2.8366 | 2.8366 |
| whole输出(token/s/卡) | 139.22 | 149.07 |
| whole TTFT均值(s) | 15.17 | 16.80 |
| whole E2E均值(s) | 29.99 | 31.64 |

native 两段约为 81.44、81.79 秒，纳入 231、232 条，实际完成速率几乎相同。在该点继续加快提交，没有提高观测到的持续产出。

whole 约提高 7.07%，这项改善也要保留。有限的 320 条请求更早进入系统，改变了升载与排空过程，但每请求平均 TTFT、E2E 更长。它反映整轮完成速度与请求等待的取舍，尚不能叫作稳态容量提高。

native 实际完成约 2.8366 req/s，平均 E2E 约 30.58 秒，两者相乘约为 86.75，接近 C88，符合大部分并发名额已经在途的状态。这个关系不能给出设备利用率或唯一瓶颈，但说明 r 还能设置得更高，并不代表系统仍有处理余量。

若目标是稳态吞吐，继续从 16 扫到 32、64 缺少新依据。短批业务若重视整轮时间，whole 改善仍有意义，是否保留还需考虑更长等待。

换成 128K 高缓存后，KV、P 新输入量与服务时间都改变，仍需重新评估 C/r，旧平台不能永久排除新场景。

## 四、Compact为什么省得不多，固定95%预算又为何更慢

Compact 尝试减少验证槽。固定宽度 6 便于组织，变长布局则有机会仅验证各请求需要的候选，SPS 根据成本和预计产出分配预算。

修复后的 Compact 与静态验证保持相同 16K 高 AL、N320/C128/r6、D 静态布局，native164.88→159.35，约 −3.35%；whole145.72→139.17，约 −4.50%。两 native 均超过 70 秒，但仍是有限配对。

宽度记录显示，可缩减的空间较少：59371 条请求级 Verify 记录中，有 56376 条仍使用宽度 6，占 94.96%。实际共使用 350746 个逻辑槽，全部按宽度 6 则为 356226，只减少 5480 个，约 1.54%。

1.54% 只描述逻辑槽数量的差异。Graph 桶、padding、Attention 与 MoE 各有执行成本，不能由这个槽数直接还原，所以它不等于设备时间、FLOPs 或端到端耗时节省。

这些计数让“能省很多计算”的预期有了边界，却没有证明哪项元数据造成了 4.50% 的回退。定位这部分成本，需要完整且能归属到 Draft/Verify 的设备计时；已有短 profile 只覆盖部分关联，CPU 提交时间或局部 Kernel 跨度无法代替。

另一个固定 95% 预算候选在相同 N320/C128/r6 下，whole158.90→155.77，约 −1.97%，AL5.7645→5.3203。基线 native 仅 59.34 秒，未达 60 秒，因而主要依据 whole，没有给出充分稳态回退结论。

少验证也可能减少每周期的有效输出。用简化的单请求模型表示，每周期输出 A、耗时 T，推进速率近似为 A/T。新旧 AL 的比值为 `5.3203 / 5.7645 ≈ 0.92294`；如果 A 也按这个比例减少，周期耗时就需要缩短超过约 7.71%，才能补回产出。这个模型只解释收支，忽略了 PD 和并发重叠，不能反推真实阶段时间。本次没有净吞吐收益，因此恢复自动预算，没有继续扫描更多比例。

95% 候选按实际验证槽算接受比例仍约 96.22%，但较小分母可以维持较高比例，同时每轮输出减少。它也缺实际生成 proposal 严格分母，后者保持 `NOT_OBSERVED`。

Compact 期间的跨请求位置错误修复则需要保留，它减少了乱码和长 SSE 停顿。性能没有提高，也不能恢复已知错误位置。正确性、功能与速度应分别记录。

## 五、专属静态EPLB布局：拟合更均衡，为什么吞吐只涨一点

专家重放置和热点副本可能减少慢 rank 的工作，但直接改变的是负载分布，最终吞吐还取决于关键路径。

16K 高 AL 的 D 专属布局在 N320/C128/r6 下，native 约 +0.35%、whole 约 +2.35%。128K 逐条 cache90.6222% 另采两端并拟合，同 N160/C64/r6 whole147.91→149.11，约 +0.81%，未取得 native。

这些结果证明采集、拟合与加载的功能链已经完成，但没有显示大幅提速，也缺少重复测量的波动范围，因此暂不认定为显著收益。

要形成吞吐收益，热点需影响完成路径，重放置需减轻慢端而非只改善均值，正式负载也需符合采集分布。若等待主要来自 P、KV、Attention 或调度，均衡专家计数无法自动消除。

本轮没有逐项定位上述条件。512 个环形槽没有保存全部请求时序；128K 的 seed/check 虽已排除在 warm 计数外，剩下的计数摘要仍不足以重建关键路径。

另一组 16K P 方案 whole +14.18%，与 D 的小幅变化不同。它说明角色、负载会改变机会，两端需分别评估，不能复制收益预期。

128K 一轮布局比较的控制器为 748.23 秒，正式仅 68.68 秒；此前模型已加载，接续与两轮预热约 255.72 秒，路由约 275.75 秒。部分时间相互包含，不能重新累加。

长期部署可以摊销准备，有限调优时间则需评估继续投入是否划算。为单次 0.81% 再冷启动，应有关键路径倾斜、代表数据或确认波动的依据，仅更均衡的分数还不够。

## 六、局部gap和低running，为什么容易把诊断带偏

CPU 小拷贝、kernel 间隔、低 running 可以是真实线索，却尚未确定能减少多少系统时间。

某个 Rank 的 Kernel 并集之外出现空隙，只能说明这些记录没有覆盖该区间。其他 Rank 可能仍在执行，异步提交也可能来自其他线程。直接把空隙占比换成吞吐收益，还额外假设了所有设备同时等待、这段等待又能消除；现有记录没有证明这些条件。

`running < C` 还可能来自 token/KV 预算、DP 分布和生命周期，不能直接推定请求不足。P 排队、D 队列低也只是供给线索，应继续连接到尾块合批这类可检验的候选。

旧 trace 的 IndexCache、Graph、并发和活跃 DP 可能不同。它可以用于降低小机会优先级，无法精确归因当前候选。

若已识别成本很小，又未证明位于关键路径，验证还需冷启动，就可先降低优先级。继续扩展 profile 和源码范围，可能挤占更有决策价值的实验。

## 七、怎样从负例得到下一步，而不是再扫一轮参数

复盘也不该将返工都写成必要探索。能改变保留决定的负例有价值；重复入口、修过期断言和核对未变逻辑，未增加相应性能信息。

一次 noCP 准备到冻结耗时 23 分 02 秒，另一次通过两轮预热与完整路由后，正式前才遇旧断言。它们属于编排损耗，不能归作模型或硬件退化。采集出错后也应先确认原请求及服务，再修原 CPU 后处理。

下一轮可根据已知结果确定动作：

| 当前证据 | 下一步更有价值的动作 | 不该自动继续的动作 |
| --- | --- | --- |
| r提高，native不变，whole变快且等待更长 | 根据稳态容量或短批完成时间选择目标 | 继续倍增r，宣称一定还有容量 |
| TPOT降低，whole/native吞吐均不增 | 追踪等待或批次组织；关闭当前组合 | 只围绕更低TPOT微调 |
| Compact大部分记录仍用满宽度 | 评估真实可变长度空间及净成本 | 默认“更紧凑”一定更快 |
| 专属布局仅有小幅单次变化 | 保留数据与健康状态，降低优先级 | 为凑显著结论重复冷启动 |
| 原正式负载尚未执行 | 修真实入口或配置合同 | 把它记成性能回退 |

重新打开旧方向时，要说明发生了什么变化。P cap2 早期负向，后来在新的 chunk、布局和高 AL 负载中正向，重试的理由是执行条件已经改变，而不是把原试验再做一遍。

只有比较条件明确、改善值得确认时，再安排长窗口。小幅单次差异可以暂不保留，无须为每个参数贴永久标签耗尽时间。应留下被排除的假设、适用条件与缺失证据，便于条件变化后重新判断。

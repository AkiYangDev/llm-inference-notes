# Ascend 910C推理调优负例分析：为什么合理的优化没有带来吞吐收益

把请求速率提高四倍，native 几乎没变，whole 却提高了；换一份专属专家布局，完整采集、拟合、加载后，吞吐只多约 0.81%。这两种结果都不适合只记一句“没用”。

本轮 DeepSeek-V4-Flash、Ascend 910C 还测了 CP 拓扑、Prefill chunk、通信轮次、DSPARK Compact。有些降低 TPOT、却少了完成吞吐，有些只改善升载；候选提出时的机制，需要与实际改变的指标对上。

下面保留每个方向当时回答了什么、缺什么，以及为什么继续或停止。它们决定了后面该换问题，还是延长确认。

数据为 2026 年 10 月 18—21 日 PD 快照、原 AISBench 统计，不含后续动态 EPLB。正向见[整体复盘](ascend-910c-inference-tuning-effective-optimizations-and-costs.md)，编排返工见[流程复盘](inference-tuning-workflow-postmortem.md)。

## 一、先分清三种不同的“没收益”

P、D 各 8 张物理卡，真实 PD 共 16。目标为 TPOT 严格小于 20ms 时提高输出，每卡均除以 16；C 限客户端在途，N 数正式请求，r 为提交速率。

16K 正文/Chat 16388、输出 1024、零缓存；128K 正文/Chat 131076、输出 1024、逐条命中 90.6222%，分别比较。普通任务、高 AL 复制集也分开。正式配对均无失败，通用业务精度尚未完成。

当前目标下 whole、native 同降，其他指标不足以抵偿，就可先不保留。这个工程决定无须先证明普适规律，单次 −1% 也不表示所有环境都慢 1%。

TPOT 更低可能不缩短整轮，提高 r 可能只减少升载。各列记录不同价值，最后按服务目标选择。

请求没发、collector 导入失败、窗口过短，则还没获得足以回答问题的性能结果。多项一起改变，也只评价联合配置。

whole 包含升载、排空，native 由原 AISBench 选择。报告同时保留，whole 的接受计数只归 whole，没有另外删慢请求。

正向同样要看两列：D Graph 加档位 6，同 N480/C88/r4，native 约 +3.93%，whole 约 +0.51%。可以保留，但两个数一起报告，收益也不跨负载累加。

## 二、减小CP、增大chunk：局部变快为何没有变成系统收益

相同 16K 普通任务、N480/C88/r4，从 CP4/DP4 改 CP2/DP8，并调整配套通信，D 与输入保持原配置。

| native指标 | 原方案 | 候选方案 |
| --- | ---: | ---: |
| 输出吞吐(token/s/卡) | 181.20 | 179.56 |
| TTFT均值(s) | 10.57 | 12.83 |
| TPOT均值(ms) | 19.3 | 17.2 |
| E2E均值(s) | 30.29 | 30.45 |

native 约 −0.91%，whole 约 −1.64%。TPOT 降了，TTFT 却增，E2E 未缩短，整组请求没有完成得更快。

CP、DP 同时改变各单元工作量、请求分布、通信形状。因此这组评价联合拓扑，尚未隔离 CP，TPOT 也无法反推出 P 某段通信耗时。

chunk 的动机则是尾块：16388 输入、有效 chunk 8192、P 接纳上限 1，最后只剩 4 Token。改 8320 能两块完成，同时通信 round1 换成 round2。

同高 AL 复制集、N320/C128/r6，结果为：

| 指标 | 8192 / round1 | 8320 / round2 |
| --- | ---: | ---: |
| native输出(token/s/卡) | 164.88 | 163.28 |
| whole输出(token/s/卡) | 145.72 | 144.76 |
| native TPOT(ms) | 7.8 | 7.0 |

native 约 −0.97%，whole 约 −0.66%。少了一块，吞吐仍没提高。阶段时间缺失，无法将回退分给新增 128 Token 还是第二轮通信，本次停的是这组联合配置。

后来保留 8192/round1，仅将接纳上限 1→2，让尾块接下一条。同 N640 native 提高 32.27%。相同尾块，换一个接纳条件，结果就不同。

下一步因此转向“还有预算为什么停止接纳”，没有继续扫描 chunk。

## 三、请求速率提高四倍：容量没涨，但不能说完全没用

r 是热参数，先改变请求到达节奏。

同 16K 普通任务、N320/C88、G5，4→16 req/s：

| 指标 | 4 req/s | 16 req/s |
| --- | ---: | ---: |
| native输出(token/s/卡) | 181.5392 | 181.5425 |
| native实际完成速率(req/s) | 2.8366 | 2.8366 |
| whole输出(token/s/卡) | 139.22 | 149.07 |
| whole TTFT均值(s) | 15.17 | 16.80 |
| whole E2E均值(s) | 29.99 | 31.64 |

native 窗口约 81.44、81.79 秒，纳入 231、232 条，实际完成速率几乎一样。这个工作点的提交已足以维持观测产出。

whole 仍改善约 7.07%。320 条更早提交，升载、排空随之改变；每请求平均 TTFT、E2E 却更长。因此有限批次完成更快，持续容量没有相应证据。

native 约 2.8366 req/s×平均 E2E 约 30.58 秒，得 86.75，接近 C88，大部分名额已被在途请求使用。它没有给出设备利用率、唯一瓶颈，却说明提高提交上限不等于增加处理余量。

稳态吞吐目标下，继续从 16 扫到 32、64 缺乏新依据。若业务只关心短批完成，whole 改善仍可与更长等待权衡。

换 128K 高缓存，KV、新输入、服务时间又变，C/r 需重新评估。

## 四、Compact为什么省得不多，固定95%预算又为何更慢

Compact 通过变长 Verify 少算候选，SPS 按预计成本、产出分预算；固定宽度 6 则较容易组织执行。

同 16K 高 AL、N320/C128/r6、D 静态布局，修复后的 Compact 与固定验证相比，native 164.88→159.35，约−3.35%；whole 145.72→139.17，约−4.50%。两 native 都超过 70 秒，仍为有限配对。

记录共 59371 次请求级 Verify，其中 56376 次仍取宽度 6，占 94.96%。实际逻辑槽 350746，全部定宽为 356226，只少 5480、约 1.54%。

1.54% 只数逻辑槽。Graph 桶、padding、Attention、MoE 实际怎样执行，不能从这个比例推回设备时间、FLOPs 或整轮收益。

省槽空间很小，已经缩小了收益预期；但 4.50% 回退具体来自哪项 metadata，仍未证明。需要完整、可归属 Draft/Verify 的设备时间，短 Profile、CPU 提交、局部 Kernel 跨度都没补齐。

另测 95% 固定预算、同 N320/C128/r6，whole 158.90→155.77，约−1.97%，AL 5.7645→5.3203。基线 native 59.34 秒未到 60，主要按 whole 判断。

单请求简化为每周期推进 A、耗时 T，速率约 A/T。AL 比例`5.3203 / 5.7645 ≈ 0.92294`，若 A 同比减少，T 就需缩短超过约 7.71% 才补回产出。这个算例忽略 PD、并发重叠，不能反推阶段时间。本轮没有净收益，恢复自动预算。

95% 候选的验证槽接受比例仍约 96.22%，较小分母可以维持高比例，同时每轮产出下降。实际生成 proposal 分母仍缺，严格接受率保持`NOT_OBSERVED`。

跨请求位置错误则必须修。修复改善乱码、长 SSE 停顿，未提速也不应恢复已知错误。

## 五、专属静态EPLB布局：拟合更均衡，为什么吞吐只涨一点

专家重放置、热点副本先改变负载分布，只有减轻完成路径上的慢端，才会变成吞吐收益。

16K 高 AL、D 专属布局、N320/C128/r6，native 约+0.35%、whole 约+2.35%；128K 逐条命中 90.6222% 另采两端，同 N160/C64/r6，whole 147.91→149.11，约+0.81%，native 缺失。

采集、拟合、加载链已完成，较大收益未出现；小幅变化也缺重复波动范围。

正式负载要符合采集分布，热点要真的拖慢完成路径，重放置还要减轻慢端，而非仅改善均值。P、KV、Attention、调度若在等别的东西，专家均衡不会自动消掉等待。

本轮还没逐项验证。512 个环形槽不含全部请求时序，128K 的 seed/check 虽已从 warm 计数排除，余下摘要仍无法重建关键路径。

16K P 方案 whole 约+14.18%，与 D 的小变化不同，两端需要各自测量。

128K 一轮布局比较，控制器 748.23 秒，正式 68.68 秒。此前模型已加载，接续和两轮预热约 255.72 秒，路由约 275.75 秒，部分阶段相互包含。

部署长期运行可摊销准备，调优时间有限则要比较继续投入的价值。为单次 0.81% 再冷启，应先有关键路径倾斜、代表数据或确认波动的理由。

## 六、局部gap和低running，为什么容易把诊断带偏

CPU 小 copy、Kernel gap、低 running 都可提供线索，尚不能直接说明系统能快多少。

一个 Rank 的 Kernel 并集没覆盖某段，只说明这些记录在那段为空。其他 Rank、线程可能仍工作。要把 gap 换成吞吐，还需证明所有设备一起等、等待又能去掉，现有记录没支持这两步。

`running < C` 可能来自 Token/KV 预算、DP 分布、请求生命周期。P 排队、D 队列低也先作为供给线索，再转成尾块合批这样的可检验改动。

旧 trace 中的 IndexCache、Graph、并发、活跃 DP 可能不同，只能帮助筛机会，难以精确归因当前配置。

如果成本已很小、关键路径未证实，验证却需冷启，可以先放低优先级，把时间留给更可能改变选择的实验。

## 七、怎样从负例得到下一步，而不是再扫一轮参数

复盘保留有决策价值的负例，也保留没有增加性能信息的返工。两者不能都叫必要探索。

noCP 准备到冻结 23 分 02 秒；另一次两轮预热、完整路由后，正式前才遇旧断言。这是编排损耗，模型、硬件尚未进入正式性能比较。采集失败也先确认原请求、服务，再修 CPU 处理。

对应下一动作可以是：

| 当前证据 | 下一步更有价值的动作 | 不该自动继续的动作 |
| --- | --- | --- |
| r提高，native不变，whole变快且等待更长 | 根据稳态容量或短批完成时间选择目标 | 继续倍增r，宣称一定还有容量 |
| TPOT降低，whole/native吞吐均不增 | 追踪等待或批次组织；关闭当前组合 | 只围绕更低TPOT微调 |
| Compact大部分记录仍用满宽度 | 评估真实可变长度空间及净成本 | 默认“更紧凑”一定更快 |
| 专属布局仅有小幅单次变化 | 保留数据与健康状态，降低优先级 | 为凑显著结论重复冷启动 |
| 原正式负载尚未执行 | 修真实入口或配置合同 | 把它记成性能回退 |

重开旧方向，先写清变化。cap2 从早期负向到后来正向，依据是 chunk、布局、高 AL 负载改变，出现了新的接纳机会。

比较条件明确、收益值得确认，再拉长窗口。单次小差异可以暂不保留，把被排除的假设、适用条件、缺证据留下，等条件变了再判断。

# Decode 已经很快了，吞吐为什么上不去？

16388 个 token，按 8192 一块处理，最后会剩下 4 个。

这 4 个 token 在当时的配置里要单独跑一个 Prefill 批次，下一条请求还在排队，也填不进来。把 P 的 `--prefill-max-requests` 从 1 调到 2 后，短尾块可以和下一条输入合批。同样 640 条请求，whole 吞吐提高了 30.26%，native 提高了 32.27%，TPOT 却略有上升。

这轮 DeepSeek-V4-Flash、Ascend 910C 实验冻结于 2026 年 10 月 21 日，[证据摘录](../../assets/decode-fast-throughput-limited-by-prefill/evidence.json)保存了配置、结果和接纳验证。其他调整见[总复盘](ascend-910c-inference-tuning-effective-optimizations-and-costs.md)。这里沿着那 4 个 token，看一次很短的尾块怎样影响整套 PD 的交付。

<a id="87ms"></a>

## 8.7ms 之外，还有 34 秒

起初看到的平均 TPOT 是 8.7ms，整套 PD 输出却只有 166.24 token/s/卡，低于 230 的目标。生成已经很快了，请求还在什么地方花时间？

cap1 的 whole 平均 TTFT 为 34.0264 秒，E2E 为 42.9285 秒。1024-token 请求从首 token 到结束约 9 秒，开始输出以前已经等了约 34 秒。TPOT 只按首输出后的时间分摊生成 token，排队、输入计算和交接都在它前面。

这 34 秒没有完整的设备阶段拆分，TTFT 里还包括 PD 交接与首 Token 执行，所以当时只能先把排查放到首输出之前。直接取 `1 / 0.0087`，得到约 115 token/s，是单请求生成速度的量级；系统还得不断处理新请求的 16K 输入，这个倒数算不出整套服务的容量。

本轮用相同 W8A8 权重，真实 PD 为 P8+D8，共 16 张 Ascend 910C，每卡吞吐都按这 16 张物理卡归一。负载是容易预测的原文复制展示集，正文 16384、Chat 输入 16388，固定输出 1024 token。

两轮均为实体 640 条、C128、6 req/s，全部成功，缓存命中 0。D 的草稿 5/verify 6、Compact 自动 SPS、IndexCache freq2 和两端静态布局相同，只改 P 单批接纳上限。下文的 whole 和 native 各沿用原统计窗口，定义见[指标说明](aisbench-whole-native-tpot-itl.md)。

<a id="c128-p"></a>

## 128 条在途请求，都在哪里

提高并发或速率也是当时的候选，目的是让 D 多积累一些可组批请求。但 cap1 的 native 平均并发已经到 128，采样又显示 P 持续排队，D 等待队列为零。

C 约束的是客户端全部在途请求，P 队列里的请求也占名额。128 条在途里，有多少已经到了 D，单凭这个并发数看不出来。

```mermaid
flowchart LR
    A[客户端在途请求 C128] --> B[P 等待队列]
    B --> C[分块 Prefill 与合批]
    C --> D[PD 状态交接]
    D --> E[Decode 持续输出]
    E --> F[完成并释放客户端名额]
```

P 完成交付，D 才能多一条生成序列。已有序列输出快，新序列却补得慢，总产出仍会受限。反过来，D 已经饱和时，P 再快也可能只是把队列挪到 D。

这次 P 有队列，已经有理由往 P 查。计算、通信和接纳限制都可能参与其中，请求槽、token、KV 预算及 DP 分布也会影响组批。沿 `PrefillAdder` 的停止接纳条件看下去，才找到单批请求槽这个限制。

<a id="16388-token-4"></a>

## 8192 的预算里，只放了 4 个 token

P 的全局 `chunked-prefill-size` 为 131072，经软件 DP16 路径折算，单实例的有效预算为 8192 token。这里的 DP16 是软件路径，不能拿来当 P8+D8 的物理卡数。

```text
16388 = 8192 + 8192 + 4
```

前两块填满预算，最后一块只剩 4 个 token。它仍得做一次模型前向和分布式操作，才能把请求交给 D，调用本身的协调工作没有随输入缩到四个而消失。

`prefill-max-requests=1` 限制 P 单批只能有一条请求。A 已经入批，即使只用掉很少的 token 预算，B 也进不来。实际 `PrefillAdder` 的 cap1 主机验证中，初始批次就是这样排列的。

```text
请求 A： [8192] → [8192] → [4]
请求 B： [8192] → [8192] → [4]
```

方括号内是本批各请求的新输入量。`[4]` 把低填充批次直接显出来了。C128 控制客户端在途，上面的单批限制仍是 1；继续提高 C，也填不上这个尾块留下的空位。

<a id="cap2"></a>

把 `prefill-max-requests` 改成 2，A 的尾块入批后，接纳器还能检查 B，从剩余页预算里截取一块。token 上限没有改。

```text
第 1 批：A 8192
第 2 批：A 8192
第 3 批：A    4 + B 8064
第 4 批：B 8192
第 5 批：B  132 + C 7936
第 6 批：C 8192
第 7 批：C  260 + 下一请求 7808
```

第 3 批里，A 的 4 个 token 按 128-token 页收费，B 因而能用 `8192 - 128 = 8064`，用不到 8188。B 再做一块 8192 后，剩下 `16388 - 8064 - 8192 = 132`，这次要收费两页，给 C 留 `8192 - 256 = 7936`。后面的请求就沿着这些接缝接下去。

请求槽增加到两个，并没有把单批新 token 上限翻倍，chunk 和页计费仍在约束它。相同 320 条、每条 16388 token，依次送入一个接纳流程，CPU 验证得到这些批次计数。

| 项目 | cap1 | cap2 |
| --- | ---: | ---: |
| 完成请求数 | 320 | 320 |
| 输入 token 总量 | 5244160 | 5244160 |
| 调度批次数 | 960 | 645 |
| 单批最大新输入 token 数 | 8192 | 8192 |

cap1 每条三批，共 960 批；cap2 用 645 批处理同样的 5244160 个输入 token。减少的是把这些输入交给执行端的次数。

这里给了宽松的可用内存，专门验证接纳与预算规则。实机还有队列、KV 和 DP 分布，批次不会保证与 CPU 序列逐条相同。短筛的一段 P 日志里，458 条 Prefill 报告有 217 条双请求批次，没有出现单请求 4-token 批次，实机也确实发生了预期的合批。

## 从 N320 短筛到 N640 确认

N320 短筛，whole 每卡从同 N 基准 158.8958 升到 199.4288 token/s，约增加 25.51%。native 到了 239.9814，但区间只有约 50.67 秒，没达到当时 60 秒的门槛。

于是继续复用热 cap2 服务，做了一次实体 N640 确认，没有重新加载、MF 或路由。此前切换与配套约花 716.50 秒，确认轮的正式窗口是 189.15 秒，控制器是 292.58 秒。准备时间单列，不放进吞吐窗口。

主对照是 cap1、cap2 各一轮 N640。C128、6 req/s，输入、输出、源码、布局和投机匹配，两轮都 640 成功、0 失败、whole 缓存 0%，native 由 AISBench 原算法选样。

| 指标 | cap1 whole | cap2 whole | cap1 native | cap2 native |
| --- | ---: | ---: | ---: | ---: |
| 纳入请求数 | 640 | 640 | 496 | 493 |
| 区间时长（s） | 246.3904 | 189.1495 | 177.2971 | 133.2282 |
| 平均系统并发 | 111.5070 | 110.8591 | 128.0000 | 127.0185 |
| TTFT 平均 / P90（s） | 34.0264 / 39.0140 | 23.1727 / 25.0642 | 37.3785 / 39.2014 | 24.7007 / 25.1003 |
| TPOT 平均 / P90（ms） | 8.7 / 9.3 | 9.4 / 9.6 | 8.8 / 9.4 | 9.4 / 9.6 |
| ITL 平均（ms） | 48.9 | 52.7 | 49.2 | 52.9 |
| E2E 平均（s） | 42.9285 | 32.7640 | 46.3392 | 34.3254 |
| 实际完成速率（req/s） | 2.5975 | 3.3836 | 2.7976 | 3.7004 |
| 输出总吞吐（token/s） | 2659.8434 | 3464.7731 | 2864.7054 | 3789.2292 |
| 输出 / PD16 物理卡（token/s） | 166.2402 | 216.5483 | 179.0441 | 236.8268 |

同 N640 对照的 whole 增加 30.26%，native 增加 32.27%。两组 native 都超过 60 秒，也都纳入至少 128 条请求；N320 的作用到决定继续确认为止，收益不跨请求数混算。

TPOT、ITL 都略升，TTFT 和 E2E 却下降了，完成速率随之提高。D 没有靠更短的生成间隔获得这次收益。

whole AL 也基本没变，cap1 是 `655360 / 114009 = 5.7483`，cap2 是 `655360 / 113988 = 5.7494`，都按输出/verify 计。草稿、verify 宽度和 D 配置相同，Compact 的实际 proposal 分母没采全，严格接受率仍为未观测。

原统计、分位数、配置和计数范围在[结果文件](../../assets/decode-fast-throughput-limited-by-prefill/evidence.json)里。ITL 沿用原流式事件定义，一次可能返回多个 token，因此与 TPOT 分列。

## 同样的 C128，更早释放的客户端名额

whole 的在途均值约等于完成速率乘平均 E2E。cap1 是 `2.5975 × 42.9285 ≈ 111.507`，cap2 是 `3.3836 × 32.7640 ≈ 110.859`。这是同组统计的算术关系，算出来的两个在途均值很接近。

每条请求的生命周期缩短约 10 秒，同样的客户端名额就能更早释放，接纳下一条。输出固定 1024 token，完成速率上去，窗口内的输出吞吐也跟着上去。

TTFT 从约 34 秒降到约 23 秒，变化集中在首 token 以前。结合输入量守恒、接纳批次减少和 P 合批日志，这次收益可以归到 P 组批与交付改善。CPU 的 645/960 说明参数如何起效，NPU 上的 30.26%/32.27% 则是系统实测，两者各自回答不同的问题。host、前向、通信和交接的细分耗时还没采全。

本轮没有固定并测量 D 活跃 batch。供给变化后，D 的请求组合也可能变化，TPOT 略升的具体原因还得靠对应批次和阶段时间解释。端到端变快与这个略升可以同时发生。

当时的目标是在平均 TPOT 小于 20ms 时尽量提高吞吐，TTFT 只作参考。cap2 保留下来的结果是 native 236.8268 token/s/PD16 卡、平均 TPOT 9.4ms、whole 216.5483，TTFT 仍有二十多秒。优先首字延迟的业务，还得按自己的要求重新选配置。

这次起作用的组合也很具体，16K 正文、Chat16388、零缓存、高 AL 复制任务，加上绑定的源码与布局。合批要有短尾块、后继请求以及足够的 token/KV 预算，换长度、缓存或请求分布，批次形状就会变化。更早的普通负载已经出现过 Pcap2 负向记录，所以我会把这份结果连同条件一起保留。

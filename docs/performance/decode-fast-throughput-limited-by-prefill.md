# Decode 已经很快了，吞吐为什么上不去？

一轮压测中，平均 TPOT 已是 8.7ms，整套 PD 输出却只有 166.24 token/s/卡，仍低于 230 的目标。

随后我们将 P 的 `--prefill-max-requests` 从 1 调至 2。在相同 640 条请求中，whole 吞吐提高 30.26%，native 提高 32.27%，平均 TPOT 反而略升。收益来自更快处理整批请求，而非继续压低生成间隔。

这一结果让排查从草稿和 Decode 转向 P 的交付。沿实际接纳流程核对后，发现 16388-token 输入最后只剩 4 token，却仍独占一个 Prefill 批次。

下文使用 2026 年 10 月 21 日的 DeepSeek-V4-Flash、Ascend 910C 冻结实验，数据和接纳验证见[证据摘录](../../assets/decode-fast-throughput-limited-by-prefill/evidence.json)。其他优化的横向关系可查[总复盘](ascend-910c-inference-tuning-effective-optimizations-and-costs.md)，本文只展开这次合批。

先从请求时间范围看低 TPOT，再查排队和尾块。后面的 whole 与 native 各用原统计窗口，定义可对照[指标说明](aisbench-whole-native-tpot-itl.md)。所有收益都限于这里保存的模型、数据和配置。

## 一、先看清这 8.7ms 包含了什么

模型为相同 W8A8，真实 PD 部署使用 P8+D8，共 16 张 Ascend 910C。每卡吞吐均用系统总输出除以这 16 张物理卡。负载是容易预测的原文复制展示集，正文 16384、Chat 输入 16388、输出固定 1024 token。

两组都发实体 640 条，C128、6 req/s，全部成功，缓存命中 0。D 的草稿 5/verify 6、Compact 自动 SPS、IndexCache freq2 和两端静态布局一致，仅改 P 单批接纳上限。

cap1 whole 平均 TTFT 为 34.0264 秒，E2E 为 42.9285 秒，TPOT 为 8.7ms。首 token 之前已占去请求的大部分时间。

TPOT 描述首输出后按 token 分摊的生成时间，没有覆盖此前的排队、输入计算与交接。1024-token 请求从首 token 到结束约 9 秒，进入输出前已等了约 34 秒，因此继续缩短生成阶段未必最有效。

这 34 秒尚未按设备阶段拆开，TTFT 同时包含排队、Prefill、PD 交接与首 Token 执行。虽然还不能指定其中哪段最长，排查范围已经可以先放在输出开始之前。

`1 / 0.0087` 约为 115 token/s，描述单请求生成的速度量级。系统却还要持续处理新请求的 16K 输入、完成交付，再按整个窗口汇总输出，两者不能使用同一分母估容量。

## 二、C128 已经打满，为什么还要看 P 端

提高并发或速率原本也是候选，希望 D 能积累更多可组批请求。

但 C 限制所有客户端在途请求，它们可能在 P 排队、执行 Prefill，也可能已经到 D。显示 128 条在途，无法说明同时 Decode 的数量。

cap1 native 平均并发已为 128。已有采样显示 P 持续排队，D 等待队列为零，因此先查 P 的供给与组批，比继续堆请求更有依据。具体是 P 内的计算、通信还是接纳限制，还要继续核对。

简化请求路径如下。每一段都可能有等待，D 中持续输出的请求只是已经走过前面的部分：

```mermaid
flowchart LR
    A[客户端在途请求 C128] --> B[P 等待队列]
    B --> C[分块 Prefill 与合批]
    C --> D[PD 状态交接]
    D --> E[Decode 持续输出]
    E --> F[完成并释放客户端名额]
```

P 完成交付，D 才新增一条可生成序列。即使已有序列生成很快，交付不足仍限制总产出；若 D 已饱和，加速 P 也可能只将排队移到 D。

因此单个 running 数不足以指导改参，还需检查请求槽、token、KV 预算和 DP 分布。要解释本批为何停止接纳，最终仍需看 `PrefillAdder` 的条件。

## 三、16388 个 token，为什么会留下一个单独的 4

P 的全局 `chunked-prefill-size` 为 131072，经软件 DP16 路径折算，单实例有效预算为 8192 token。这里的 DP 与 P8+D8 物理卡统计属于不同口径。

16388-token 输入因此分为：

```text
16388 = 8192 + 8192 + 4
```

前两块填满预算，尾部只剩 4 token，仍需完成模型前向与分布式操作后才能交给 D。新增输入虽少，一次调用的协调工作仍然存在。

C128 控制客户端在途，`prefill-max-requests=1` 控制 P 单批请求槽。单批已有一条请求时，即使 token 预算未用满，也无法再接第二条。

实际 `PrefillAdder` 的 cap1 主机验证给出以下初始批次：

```text
请求 A： [8192] → [8192] → [4]
请求 B： [8192] → [8192] → [4]
```

方括号表示本批各请求的新输入量，`[4]` 即孤立尾块。预算设为 8192，并未保证每批都有同样多的新 token。

继续提高 C，也不会取消单批一条的限制。只要这条接纳规则不变，短尾块仍可能独占一次执行，更多在途请求无法直接填上它留下的预算。

## 四、cap2 改变了批次的接缝

改为 `prefill-max-requests=2` 后，A 的尾块入批，接纳器还可检查 B，按剩余页预算截取下一条输入。token 上限保持原值。

实际方法的验证序列为：

```text
第 1 批：A 8192
第 2 批：A 8192
第 3 批：A    4 + B 8064
第 4 批：B 8192
第 5 批：B  132 + C 7936
第 6 批：C 8192
第 7 批：C  260 + 下一请求 7808
```

B 在第 3 批处理 8064、下批再处理 8192，留下 `16388 - 8064 - 8192 = 132`。它的尾块再与 C 接上，后续同样按预算推进。

A 的 4 token 会按 128-token 页收费，所以 B 只能使用 `8192 - 128 = 8064`，而非 8188。B 的 132 收费两页，下一条 C 可用 `8192 - 256 = 7936`。

cap2 增加了请求槽，使短尾块能与下一条输入共批。单批新 token 仍受 chunk 和页计费约束，没有翻倍。

将相同 320 条、每条 16388 token 依次送入一个接纳流程，CPU 结果为：

| 项目 | cap1 | cap2 |
| --- | ---: | ---: |
| 完成请求数 | 320 | 320 |
| 输入 token 总量 | 5244160 | 5244160 |
| 调度批次数 | 960 | 645 |
| 单批最大新输入 token 数 | 8192 | 8192 |

cap1 每条三批，共 960；cap2 为 645。总 token 相同，减少的是将这些输入交给执行端的次数。

CPU 验证提供了宽松的可用内存，专门检查接纳与预算规则。实机的队列、KV 和 DP 分布仍会改变具体批次，因此它只证明参数改变了预期行为，实际速度另由 NPU 测量。

短筛的一段 P 日志中，458 条 Prefill 报告有 217 条双请求批次，未出现单请求 4-token 批次。它覆盖短筛窗口，支持与 CPU 检查相同的调度变化。

## 五、先得到一个信号，再做同负载确认

N320 短筛的 whole 每卡由同 N 基准 158.8958 升至 199.4288 token/s，约 +25.51%。native 达 239.9814，但区间仅约 50.67 秒。

短筛不足当时 60 秒门槛，因此继续用热 cap2 服务做一次实体 N640 确认，没有再加载、MF 或路由。此前切换与配套约耗 716.50 秒，确认正式窗口为 189.15 秒、控制器为 292.58 秒。准备单独记账，不加入吞吐窗口。

主对照按 cap1、cap2 各一轮 N640，C128、6 req/s，输入、输出、源码、布局及投机匹配。两轮均 640 成功、0 失败、whole 缓存 0%，native 为 AISBench 原算法选样。

whole 提高 30.26%，native 提高 32.27%，两组 native 都超过 60 秒、纳入至少 128 条请求。N320 只用于决定是否继续确认；这里的收益来自同 N640 对照，不混用不同请求数。

cap2 的 TPOT、ITL 略增，TTFT、E2E 却显著下降，完成速率提高。指标组合更支持 P 供给与请求等待的解释，未证明 Decode 算子变快。

whole AL 基本不变：cap1 为 `655360 / 114009 = 5.7483`，cap2 为 `655360 / 113988 = 5.7494`，均按输出/verify。草稿、verify 宽度和 D 配置相同，Compact 实际 proposal 分母未采全，因此严格接受率仍为未观测。

原统计、分位数、配置及计数范围见[结果文件](../../assets/decode-fast-throughput-limited-by-prefill/evidence.json)。ITL 沿用原流式事件定义，可能包含一次多 token 返回，与 TPOT 分开。

## 六、吞吐提高时，请求究竟少等了什么

whole 中在途均值约等于完成速率乘平均 E2E：cap1 `2.5975 × 42.9285 ≈ 111.507`，cap2 `3.3836 × 32.7640 ≈ 110.859`。这是同组统计的算术关系，并非新的独立测量。

在途数量接近，每条生命周期却缩短约 10 秒，同样的客户端名额便能更快释放、接纳后续请求。固定输出 1024 时，完成速率提高就增加了输出吞吐。

TTFT 由约 34 秒降至约 23 秒，变化集中于首 token 之前，后续 TPOT 未改善。结合输入守恒、接纳批次减少和真实 P 合批日志，本轮将收益归于 P 组批与交付改善。

更细的 host、前向、通信与交接耗时仍未采全。CPU 的 645/960 描述机制，实机 30.26%/32.27% 描述系统表现，各自不能替代另一项证据。

本轮未固定并测量 D 活跃 batch。供给改变后，D 请求组合可能随之改变，因此 TPOT 略升也不与端到端提速冲突。要解释这部分差别，还需 D 的对应批次与阶段时间。

TTFT 改善后仍有二十多秒。当时目标是在平均 TPOT 小于 20ms 时尽量提高吞吐，TTFT 作为参考；若业务优先首字延迟，配置选择需按相应要求重新判断。

## 七、下一次再看到“低 TPOT、低吞吐”

再遇到低 TPOT、低吞吐，我会先分首 token 前后时间，再查在途请求的位置。TPOT 容易漏掉输入与交接，C 满又可能只是排队，二者都不能单独证明 D 饱和。

之后将全局 CLI、单 DP 有效 chunk、页大小和请求槽一起核对。实际输入 16388 与“16K”标签之间那 4 token，正是本例发现低填充批次的关键。

候选应只改变相关变量。cap1→2 需要短尾块、后继请求，以及足够 token/KV 预算；换长度、缓存或分布后，合批形状会变。更早普通负载中已有 Pcap2 负向记录，因此不能脱离条件推广。

这次保留的完整组合是 16K 正文、Chat16388、零缓存、高 AL 复制任务及绑定的源码、布局。它的 native 为 236.8268 token/s/PD16 卡，平均 TPOT9.4ms，whole216.5483；后续比较应继续使用同等条件。

从首 token 前的等待向前查，我们才找到 P 批次中的短尾块。D 上已经输出的请求很快，并没有说明新请求也能及时进入生成。

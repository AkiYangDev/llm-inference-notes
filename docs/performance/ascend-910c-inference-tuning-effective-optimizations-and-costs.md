# 一次Ascend 910C推理调优复盘：真正有效的优化、失败假设与实验成本

这轮 DeepSeek-V4-Flash 调优中，收益最明确的改动，是把 P 的 `--prefill-max-requests` 从 1 调到 2。同为 N640 的对照里，native 每卡输出从 179.04 提到 236.83 token/s，提高 32.27%；whole 则提高了 30.26%。

其他方向没有带来同等收益。DSPARK Compact 修复正确性后，在独立对照中仍未提高吞吐；128K 专属静态布局完成了采集、拟合与加载，同负载的吞吐也只提高约 0.81%。

把这些结果放在同一轮复盘中，可以分清功能适配、正确性修复与性能收益，也能看到最终配置是如何逐项保留的。

材料来自 2026 年 10 月 18—21 日的 PD 固定快照，没有混入后续动态 EPLB，也未代表当前上游默认。编排返工另见[流程复盘](inference-tuning-workflow-postmortem.md)，本文主要记录有效改动、失败假设和实际成本。

关于小收益和负例的逐项推演，另见[负例分析：为什么合理的优化没有带来吞吐收益](ascend-910c-inference-tuning-negative-results-and-stop-rules.md)，其中补充了到达速率的whole变化，以及Compact实际逻辑验证槽的节省空间。

## 一、先明确：这次究竟优化什么

真实 PD 中，P 处理输入并交接 KV，D 继续生成。P、D 各 8 张 Ascend 910C，共 16 张物理卡。每卡统一用系统输出除以这 16 张，未按逻辑 rank 或只按 D8 归一化。

目标是在平均 TPOT 严格低于 20ms 时，使 native 输出超过 230 token/s/卡。TTFT 仍报告，但本次不作为淘汰条件，因此达到吞吐目标不等于满足所有在线业务的首字要求。

实验分两个独立场景：16K/1K/零缓存，以及 128K/1K/逐请求至少 90% 前缀命中。后期都使用易预测的原文复制展示集，用于观察高接受长度，不能代表一般问答、代码或推理任务的服务容量。

正文和 Chat 实际长度分别核对：16K 为 16384→16388，128K 为 131072→131076。各正式输出实际完成 1024 token，没有通过提前结束减少工作；组内权重和 W8A8 一致。

whole 覆盖升载、正式请求和排空，native 由 AISBench 原算法选择，没有自删慢请求。项目要求至少 128 样本、60 秒以排除短窗，但这仍不是长期稳定或显著性证明。

最终两组满足要求的结果如下。时延为窗口均值，正式请求全部成功，失败为 0。

| 场景与统计窗口 | 纳入请求数 | 时间(s) | TTFT(s) | TPOT(ms) | E2E(s) | 输出吞吐(token/s/卡) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 16K 零缓存，native | 493 | 133.23 | 24.70 | 9.4 | 34.33 | 236.83 |
| 同轮 whole | 640 | 189.15 | 23.17 | 9.4 | 32.76 | 216.55 |
| 128K、缓存90.6222%，native | 549 | 143.49 | 12.25 | 10.4 | 22.87 | 244.86 |
| 同轮 whole | 640 | 179.58 | 12.68 | 10.3 | 23.24 | 228.09 |

16K 为 C128，128K 为 C90，两者 r6。C 是客户端上限，不等于平均并发或完成速率。配置与负载不同，236.83 和 244.86 不能直接用于计算跨场景收益，条件见[数值摘录](../../assets/ascend-910c-tuning-retrospective/measurements.csv)。

## 二、最有效的改变：让四个token的尾块有机会合批

初期的重点是 D 的草稿、Graph、Verify 和布局。后来 AL 已在 5.7 左右，TPOT 也降到几毫秒，系统吞吐却仍然较低。这时继续提高接受长度，未必还能增加整套 PD 的产出。

采样显示 P 持续排队，D 的等待队列较少。它还不能证明唯一瓶颈，但提供了下一轮方向：检查 P 怎样分块，以及单批剩余的预算能否继续接纳请求。

P 使用 noCP/DP16，全局 `chunked-prefill-size=131072` 经该版本折算后，有效 chunk 为 8192。在请求上限为 1 的 CPU 接纳验证中，16388-token 请求被拆为：

```text
请求 A：8192 → 8192 → 4
请求 B：8192 → 8192 → 4
```

最后 4 token 仍独占一次调度与前向。工作量小不代表调用和协调成本也同比消失。

token 预算 8192 与 `prefill-max-requests` 分别限制输入量和请求数。上限 1 时，已有尾块便不能再接下一条；改为 2，才可能用剩余预算处理后继输入。

验证使用实际 `PrefillAdder`，没有另写理想装箱。上限放开后得到：

```text
cap1：[8192] → [8192] → [4] → [8192] …
cap2：[8192] → [8192] → [4, 8064] → [8192] → [132, 7936] …
```

第二行来自 CPU 验证，不是设备时间线，也没有保证每批都填满 8192。同样 320 条请求、输入 Token 守恒时，批次数从 960 降为 645，证明合批路径可以发生。批次形状变化还会影响设备执行与通信，不能按减少的轮数直接预测加速比。

设备日志的已观察窗口中出现了双请求 Prefill，未再看到独立的 4-token 批次。这支持尾块合批的解释，不过日志缺少完整请求 ID 与逐次设备时间，判断是否保留仍以匹配压测为依据。

N640 确认固定数据、C128、r6、布局、Compact、IndexCache 与采样，仅改 P 上限 1→2：

| 指标 | cap1 | cap2 | 变化 |
| --- | ---: | ---: | ---: |
| native 输出吞吐(token/s/卡) | 179.04 | 236.83 | +32.27% |
| whole 输出吞吐(token/s/卡) | 166.24 | 216.55 | +30.26% |
| native 平均TPOT(ms) | 8.8 | 9.4 | 略有增加 |
| native 平均TTFT(s) | 37.38 | 24.70 | 降低 |

对照中 TPOT 略升，TTFT 降低，系统输出增加。收益因此更符合 P 改善组批与供给的解释，而不是 D 单条请求生成得更快。

早期另一组负载中，P cap2 曾经负向，这个结果和当时条件也要一并保存。本轮正向依赖当前 chunk、长度、布局、投机与并发，不能泛化成上限 2 总是更好；当这些条件变化后，也有理由重新评估旧方向。

## 三、另外两类正向结果：IndexCache与P端静态布局

IndexCache 在同一份 16K 普通任务、N640/C64/r3 的配对中，native 从 164.10 提到 172.99 token/s/卡，约提高 5.41%；whole 从 147.01 提到 152.08，约提高 3.45%。native TPOT 则从 18.9 降到 17.7ms。

它跨层复用 TopK，减少重复选择，同时改变了当前层的索引行为。本轮启用的是绑定的已有实现，并完成了性能对照；完整质量评估尚未进行，因此还不能称为无损。

静态布局先采集路由再调整专家放置，热点必要时分配副本，尝试减轻慢 rank。P 候选为 272 物理槽、含 16 冗余，D 候选为 256 槽。

P 的输入与 D 的草稿/验证可能产生不同热点，16K 零缓存和 128K 高缓存也不同，因此分别采集，并在场景变化后重新判断代表性。

16K 高 AL、N320/C128/r6 中，P 从原布局+dynamic 分发切为场景布局+static，whole139.17→158.90、约+14.18%。这是布局与分发组合，未启用在线重排，也未分离各自贡献。候选 native 仅 59.34 秒，未作充分稳态证明。

D 同 N320 专属布局只有 native 约+0.35%、whole 约+2.35%。128K warm90% 另采两端，同 N160/C64/r6 whole147.91→149.11、约+0.81%。

这些小差异没有重复实验的波动范围，尚不能认定为显著收益。拟合后的分布更均衡，也不证明真实关键路径同比缩短，因此不能按均衡分数直接预测吞吐。

采集过程中还遇到过 HCCL dump 分配失败。后续把统计转到 CPU，使用成员相同的 Gloo 组做整数 SUM，由 rank0 保存，才取得可用文件。正式轮关闭了记录器，这项修复解决的是采集流程，并非逐 Token 性能优化。

布局与分发的区别详见[P端场景静态EPLB专题](ascend-910c-prefill-scenario-static-eplb.md)。

## 四、Compact为什么没有成为这轮的吞吐突破口

草稿 3、Verify 宽度 4 的配置，理论上就无法达到 AL≈5.5。因此先把草稿改为 5、Verify 宽度改为 6，再研究高接受长度与 Compact 能否减少实际验证工作。

Compact 以变长候选配合 SPS 规划，启用环境变量和成本表只是进入执行路径。SPS 表用于投机预算，与决定专家放置的 EPLB 文件不同。

PD 中本地没有请求的 worker 仍需参与本轮 collective，但 dummy 行不能写入有效的压缩状态。Ragged 长度还必须一路传到压缩位置、Graph 桶和 Replay 元数据，单个分支跑通不足以证明整条路径正确。

其中 `dsv4_common_hooks.py` 的一处位置计算仍假设每条请求固定验证 6 Token。变长请求同批时，这个假设可能让写入位置越过本请求，落到另一条请求。

CPU 最小反例通过实际安装 hook/backend 复现位置错误。修复后，同普通数据 320 请求中替换字符超过 10 的请求由 14 降为 0，最大 SSE 间隔 58.26→1.59 秒；native 约−3.59%，whole 基本持平。

错误的位置计算不能为了速度再恢复，所以本轮保留了修复。替换字符与长停顿减少，说明已观察到的异常改善，仍不等于完成了任务正确率认证。

修复后的高 AL 配对中，Compact 相对静态验证 native 约−3.35%、whole 约−4.50%。规划、元数据、长度和 shape 都可能影响成本，但短 profile 未可靠分离完整 draft/verify 设备时间，尚无单项根因。

固定 95% 预算的同 N320/C128/r6 对照中，whole 从 158.90 降到 155.77，AL 从 5.7645 降到 5.3203。减少验证也可能减少每轮有效产出；这次没有净收益，因此恢复自动预算。

后续组合保留了修复后的 Compact，再叠加 P 布局与 P cap2。由于缺少同新布局、同 P cap2 下关闭 Compact 的对照，不能从最终高分倒推 Compact 独立提速。

## 五、合理的假设怎样变成负例

其余候选的主要观察如下，应结合各自假设和比较范围阅读：

| 尝试 | 观察结果 | 结论范围 |
| --- | --- | --- |
| P有效chunk8192/round1改为8320/round2 | native约−0.97%，whole约−0.66%，TPOT却更低 | 这组几何与通信配置没有提高完成吞吐，不能只凭局部延迟保留 |
| 原场景请求速率4→16 req/s | native约181.5392→181.5425，基本不变 | 该场景继续提高提交速率没有提高处理能力，不代表新场景也无效 |
| CP4改为CP2 | 同负载native约−0.91%，whole约−1.64% | 减少并行通信不自动带来净收益 |
| D graph档位加入6 | 同N480 native约+3.93%，whole约+0.51% | 短筛正向，但不能只展示较大的native涨幅 |

这些都是有限次数观测。无新依据时可关闭小幅负向候选，避免长确认；条件改变后仍可重新提出试验，旧速率平台不能限制所有新场景。

旧 profile 中的 rank 间隙也不能直接用作可回收预算。其他 rank 可能仍运行，host 提交不等于完整设备阶段，IndexCache、Graph 及活跃 DP 也未必与当前配置一致。

因此没有围绕小 copy 和局部 gap 无限追加冷启动。它们有诊断价值，但未解释整机吞吐缺口，优先级转向能改变批次和 P/D 供给的候选。

AL 在本文按整轮输出/verify 计算，受首 token 和截断影响，与严格接受率不同。Compact 实际验证槽未必等于实际生成 proposal，不能由固定 gamma 补造后者，也不能用 `(AL-1)/gamma` 冒充实测。

16K 与 128K C90 的 whole AL 为 5.7494、5.7760，实际验证槽接受比例为 96.1613%、96.4122%。实际生成草稿严格分母未完整采到，标 `NOT_OBSERVED`，整轮计数也未复制到 native。

## 六、128K实验提醒我：缓存和并发可以改变答案

128K 高缓存改变了新增输入、KV 占用和 D 历史访问，因此需要重新评估，而非只按正文长度倍增工作量。

首版公共区 page128 对齐后预测约 89.9387%，已经不达标。调整数据并按 DP 做独立 seed/check 后，正式逐条达到：

```text
实际缓存token / 实际输入token
= 118784 / 131076
= 90.6222%
```

配置 90%、平均 90% 和每条至少 90% 不同。跨轮复用数据还可能命中后缀，因此同 N640 的 C128/C90 先清旧缓存，再各做 16seed、16check，准备另计，否则会将缓存变化算成并发收益。

whole C128 为 240.37、C90 为 228.09 token/s/卡，约−5.11%。C90 同时使 TTFT18.14→12.68 秒、TPOT11.5→10.3ms、E2E29.91→23.24 秒，需要按容量与等待的目标取舍。

C90 native 选 549 条、143.49 秒，输出 244.86、TPOT10.4ms，满足本项目要求。C128 native 因 CPU 导入失败缺失，不能用其 whole240.37 与 C90 native244.86 直接比较。

native 描述原算法选中请求区间的表现，whole 描述有限整轮的表现。达到 native 目标后，升载、排空和等待代价仍需报告；选中区间也不能单独证明长期稳定容量。

## 七、实验成本里，哪些是必要工作，哪些是可避免损耗

有依据的短负例能改变下一步选择，并不等于浪费。可避免的损耗，是没有新条件仍重复已否定方向，或正式请求还未发出，时间就已耗在入口适配与过期断言上。

一次 noCP 从准备到冻结用了 23 分 02 秒；后续控制器完成两轮预热与 256 条路由验证，才在正式请求前被旧环境断言终止。这轮没有进入正式性能测试，暴露的是配置一致性检查太晚。

其他例子包括 DP16 被末尾改成 DP4/CP、dispatch128 被 helper 改回 64、父进程类可用而 worker registry 构建失败，以及推理完成后 native 子进程缺 payload 导入路径。

检查应覆盖实际边界：生成配置、dump、新进程重载、真实入口和子进程环境。未变化代码、分词和证明直接复用，不每改 C 重核一遍。

也有必须单列的准备成本：

| 事件 | 控制器墙时 | 正式窗口 | 需要怎样解释 |
| --- | ---: | ---: | --- |
| 一次128K布局比较 | 748.23s | 68.68s | 本轮模型已加载，但新布局下两轮预热和路由验证仍分别花约255.72s、275.75s |
| 最后一轮128K C90热测 | 309.16s | 179.58s | 新增启动、预热、路由均为0，缓存seed/check仍花47.91s |

C90 的控制器耗时比正式推理多 129.58 秒，扣除缓存准备仍约 81.67 秒，分布在前置与收尾阶段，尚缺完整拆分。这部分不能全部视为必要成本，也还没有被消除。统计时，嵌套阶段不能重复求和，逐请求延迟相加也不能代替并行墙时。

两轮预热、完整路由当时属于服务变更流程，缩减未完成等效验证，不能事后全部删去。但纯 N/C/r 且服务代码未变时应保持热状态，缓存清理、seed/check 另外核算。

如果推理已经完成、服务健康，只是 CPU 汇总缺模块，就修原环境、读原数据；一端启动成功而另一端失败，也先保留成功端。重发请求或机械回滚，可能增加本可避免的加载成本。

流程改进应落实到可观察结果：热参数只准备一份 CASE、候选有明确取舍、负例及时停止、原结果一次收齐，收尾错误无需重发模型。规则文件增加并不能代替这些结果。

这轮最强收益来自 P 合批，IndexCache 和 P 静态方案也有匹配正向；Compact 主要保留正确性修复，D 布局和部分 Graph 差别较小。继续工作还需补真实任务质量、实际 proposal 分母及完整 draft/verify 成本，高 AL 展示成绩没有替代这些验证。

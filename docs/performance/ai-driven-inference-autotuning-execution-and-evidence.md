# 一轮实验什么时候算完成：全自动调优的状态、证据与恢复

640 条请求已全部成功，终端却非零退出。这轮究竟在哪个阶段失败，是否还有必要重发？

那次 DeepSeek-V4-Flash、Ascend 910C 试验的失败点在 native 汇总子进程：它无法导入本轮自定义模块。确认请求已经结束、服务健康后，只补齐子进程环境，用原 AISBench selector 处理原数据，就得到了结果，没有重发模型请求。

总命令包含部署、预热、推理、采集和报告，一个退出码无法表达各段状态。如果仅凭 shell 失败就重跑，可能丢弃已经完成的 640 条请求和可复用的热服务，再支付一次启动成本。

[上一篇](ai-driven-inference-autotuning-decision-loop.md)讨论怎样选候选，这里沿配置、执行、结束和报告追踪一次实验，说明故障后可以从何处接续。例子来自实际工具链，整理建议也限定在这些问题上。

## 一、实验配置要能一路追到实际执行

一份配置从文件走到实际执行，还要经过脚本追加参数、helper 环境、远端检查和报告读取。任何一处残留旧值，都可能让几份都叫“当前配置”的内容互不一致。

例如基础配置中的 DP16 可能被命令末尾覆盖成 DP4/CP4，外层设置的 dispatch 容量也可能被 helper 改回旧值。默认文件只能说明起点，最终运行身份还要从实际参数和加载结果确认。

核对时，我把计划中的数据版本、长度、N/C/r、缓存条件和服务变更，逐项对应到最终参数、实际加载的源码/布局与运行实例。只有两边一致，报告才能归到这个候选名下。

重新整理时可保存以下字段，格式仅为示意：

```json
{
  "scenario": "copy-128k-1k-prefix90",
  "dataset_id": "immutable-dataset-version",
  "load": {"requests": 640, "concurrency": 90, "request_rate": 6},
  "service_parent": "verified-service-identity",
  "delta": {"concurrency": {"from": 128, "to": 90}},
  "measurement": {"whole": true, "native": true},
  "recovery_target": "verified-service-identity"
}
```

示例只改 C，父配置和恢复目标都不变，执行器应直接走热测。若又要新写部署代码，说明入口可能仍有历史硬编码。

数据也要有独立身份。N640 需要 640 条实体请求，切出的子集另存版本与哈希；生成时记录 tokenizer、正文与 Chat 包装后的长度、目标输出和唯一后缀。后续条件未变，就直接复用，不必每轮重新分词。

## 二、执行阶段比一个总退出码更有用

PD 一轮可能经过候选准备、服务预热、路由验证、缓存准备、正式请求、结束确认、后处理和保留决策。只改 C 的热测没有新增加载、MF 预热和路由验证，在阶段记录中写清复用即可。

正式开始前确认服务身份，并确保只有这一轮负载；结束后核查原客户端和请求；汇总时关联原数据及处理版本。每阶段保存足以支持下一步判断的事实，不必再写一份庞大的状态说明。

本地命令退出，不代表远端已经结束；摘要里的 RUNNING 也可能落后于原进程和退出文件。两者冲突时，应核对当轮进程与产物，不能凭一个旧状态字符串决定是否重启。

每轮只设一位设备任务 owner，负责开始、结束及相关 API。其他工作读取它的状态或离线数据；已有 watcher 时，不再启动第二份 collector，避免并发写结果、释放占用或重复调用统计接口。

调用端遇到网络超时，远端可能已经执行。恢复连接后，用阶段身份和开始/完成记录确认它走到了哪里。锁负责阻止第二轮负载进入，原产物则提供第一轮的进展证据。

## 三、检查应该放在副作用之前

检查最值得放在即将付出昂贵成本之前。

服务变更前核最终命令、来源和恢复对象；正式请求前检查入口能否识别本轮模式；后处理前检查新进程能否加载原配置。这些检查大多可以在 CPU 上完成，不必触发模型请求。

AISBench 的类能在父进程里构造，不代表配置经过生成、dump、reload 后，worker 仍能通过 registry 构建它。后来让检查经过新进程与真实构建入口，才覆盖了实际失败的位置。重复验证父进程构造，无法发现这类问题。

增大 N 还要检查底层 collector 的白名单和文件限制。仅改 C 且 tokenizer、解析、统计未变时，则继承既有证明。

可用以下变更表限定本次核对范围：

| 本轮变化 | 应检查的主要边界 | 可以继承的事实 |
| --- | --- | --- |
| N、C、r | 实际参数、实体数量、受影响的采集边界 | 未变服务源码、tokenizer、观测逻辑 |
| AIS 扩展 | 配置生成、dump、fresh-process reload、受影响的 worker 路径 | 未变模型服务 |
| 服务源码或布局 | 最终运行身份、容量与相应服务验证、恢复对象 | 未变数据与计量定义 |
| 后处理环境 | 原数据绑定、子进程导入与原 selector | 已成功的正式推理 |

热参数点可以继承已完成的预热与路由验证，服务发生变化时再安排相应准备。至于服务重启后需要的预热长度、路由数量能否进一步缩减，目前没有等效验证，仍保留原有步骤。

## 四、数据与缓存决定这轮到底测了什么

128K/1K、约 90% 缓存需要同时处理分词、Chat 包装、页边界和路由。公共文本长，并不保证服务实际命中达标，验收仍读取逐请求 cached token。

本轮正文为 131072 Token，Chat 包装后为 131076，输出固定 1024。最终每条请求都命中 118784 Token，以实际 Chat 输入为分母，命中率为 90.6222%。初版页对齐预测却还低于 90%，所以“约九成”和“每条至少九成”必须分别验收。

多个 DP 目标各自维护缓存时，一个目标预热成功，不能证明其他目标也已就绪。本轮先用独立 seed 准备缓存，再逐路由 check，之后才发正式请求；准备请求数和时间另行记录。

跨轮重复后缀还可能提高实际命中。固定约 90% 场景要防止额外复用被算成参数收益，零缓存也需相应唯一性和状态控制。

报告保留正文、Chat、实际输出、命中范围及分母。名义输入吞吐可以展示承载量，但不能把已命中位置都算作本轮新增计算。

## 五、结果记录要允许“未知”，也要保留统计区间

最早报告没交齐 ITL，我追问后才补上。应将成功数、完整时延、吞吐窗口与接受计数一次汇总，避免每问一项就重新找数据。

TPOT 将时间摊到输出 Token，ITL 则来自输出事件的间隔。投机一次提交多枚 Token，加上缓冲与传输，会改变客户端观察到的到达节奏，因此两者可能相差很大。Draft、Verify 的设备耗时还要在对应执行阶段单独测量。

128K C90 的 whole AL 为 `655360 / 113463 = 5.7760`，分子是输出数，分母是 Verify 次数。这个口径包含首 Token、额外 Token 和结束截断的影响，应连同计数定义一起阅读。

Compact 已采集 Verify cap 槽位计数，却没有完整的实际草稿数，因此严格 proposal 接受率保留为 `NOT_OBSERVED`。能够计算 AL，不代表严格接受率所需的分母也已经具备。

接受计数留在原窗口，native 请求集与时段另存。这样 244.86 还能对应到具体样本、时长和卡数。

以下同轮 C90 使用 P8+D8 共 16 卡、实体 N640、r6、逐条缓存 90.6222%、输出 1024：

| 指标 | whole | AISBench native |
| --- | ---: | ---: |
| 纳入请求数 | 640 | 549 |
| 时间（s） | 179.5766 | 143.4935 |
| 平均系统并发 | 82.8179 | 87.4978 |
| 平均 TPOT（ms） | 10.3 | 10.4 |
| 输出吞吐（tok/s/PD16 卡） | 228.0921 | 244.8612 |
| AL | 5.7760 | 未单独采集 |

native 满足项目的样本量与时长要求，但 AL 只在 whole 中采集，因此表中保留不同指标各自的实际覆盖范围。完整数值见[结果摘录](../../assets/inference-tuning-workflow-postmortem/measurements.csv)。

## 六、失败以后，沿已经完成的阶段恢复

失败位置决定恢复分支，而非统一重跑。

如果配置或导入在连接模型之前失败，正式请求数为零，就先修入口，再继续准备。如果服务已经加载、预热完成，只是入口不识别本轮模式，就保留热状态接续，不重复安装 observer 或加载模型。这两种故障都不能登记为性能负例。

推理结束后采集失败，先独立核对原客户端和服务状态，再修原数据处理。开头那次故障保存了原错误，补齐 payload 搜索路径后复用原 AIS 算法，没有改变计时，也没有重发请求。

如果 start/end 或统计 API 的状态未知，先保留 owner，核查原进程、文件和完成证据。再次 start 可能重置状态，dump 也可能有副作用；恢复网络后的第一步应是查明事实，而不是重放全部阶段。

回滚先确定恢复对象。源码、布局和场景已演进，默认脚本可能落后，应在候选开始前保存父身份。纯性能负向则先保留结果，再按后续计划切换。

只接续未完成阶段，才能复用前面工作。状态未知则先查明，让下一负载有明确起点。

## 七、跨会话继续，靠短入口和可靠产物

数天实验会跨上下文。每次复制全历史既耗 token，也容易将旧 RUNNING、PID、未完成记录误读为当前事实。

交接入口只需当前授权、场景与服务父身份、owner、已完成阶段和下一动作。详细失败、日志和实验各留目录，按需查索引。

摘要用于阅读，原结束文件、统计和变更回执用于举证。后处理修好后更新当前结果，保留旧错误；既不抹去失败，也不让过期 PENDING 覆盖新成功。

进度应报告实际阶段：请求尚未发出、模型加载中、正式请求已发，或推理结束而采集失败。普通等待可以静默；重要故障则说明失败边界、设备占用和是否可能重复请求，比一句“快好了”更有用。

现有薄适配器仍有硬编码，需要先收敛执行、记录与汇总到共享入口，由计划层提供本次输入。能否在下次纯 C 变更快速发出、零新增加载、一次交齐报告，才是实际验收。

结束至少包含负载终止、结果提取和足够决策三项。有时前两项完成，仍缺接受分母或足够确认窗口，应补相应证据，而非默认再跑一次。

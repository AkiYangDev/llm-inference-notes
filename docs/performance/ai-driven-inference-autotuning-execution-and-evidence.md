# 一轮实验什么时候算完成：全自动调优的状态、证据与恢复

640 条请求已经全成功，终端却非零退出。若只看总退出码，这轮就会被重跑一次。

那次 DeepSeek-V4-Flash、Ascend 910C 的故障在 native 汇总子进程：自定义模块导入失败。核对请求已结束、服务健康后，补齐子进程环境，再用原 AISBench selector 处理原数据，结果就恢复了，没有重发模型请求。

部署、预热、推理、采集、报告共用一个总命令，却不共享完成状态。已经得到的 640 条结果、可复用热服务，要从失败的后处理里分出来。

[上一篇](ai-driven-inference-autotuning-decision-loop.md) 讲候选选择，这篇跟踪一次实验的配置、执行、结束与报告，沿实际工具故障说明从哪里接续。

## 一、实验配置要能一路追到实际执行

配置文件离实际执行还有脚本、helper、远端检查、报告读取几层。旧值留在任一层，都可能让“当前配置”指向不同东西。

例如基础文件写 DP16，命令末尾可能覆盖为 DP4/CP4；外层设 dispatch 容量，helper 又可能改回旧值。这些情况都需要追到最终参数、加载结果。

我把计划的数据版本、长度、N/C/r、缓存、服务变化，对到最终参数、实际源码/布局、运行实例。结果归到候选名下，依靠的是这些对应关系。

记录可以保存以下字段，格式仅为示意：

```json
{
  "scenario": "copy-128k-1k-prefix90",
  "dataset_id": "immutable-dataset-version",
  "load": {"requests": 640, "concurrency": 90, "request_rate": 6},
  "service_parent": "verified-service-identity",
  "delta": {"concurrency": {"from": 128, "to": 90}},
  "measurement": {"whole": true, "native": true},
  "recovery_target": "verified-service-identity"
}
```

例中只改 C，父配置、恢复目标都不变，执行器应走热测。纯 C 变更仍触发新部署，通常需要回查入口的硬编码。

数据独立标识。N640 对应 640 条实体请求，子集另存版本、哈希；生成时记 tokenizer、正文与 Chat 长度、目标输出、唯一后缀。条件没变就直接复用。

## 二、执行阶段比一个总退出码更有用

PD 可以分成候选准备、服务预热、路由验证、缓存准备、正式请求、结束确认、后处理、保留决策。只改 C 的热测复用加载、MF 预热、路由证明，在本轮记录标明即可。

开始前核服务身份、单一负载，结束后核原客户端、请求，汇总时关联原数据和处理版本。阶段记录只保存支持接下来判断的事实。

本地退出时远端可能还在运行，摘要 RUNNING 也可能落后。状态冲突，就核当轮进程、结束文件与产物。

设备任务由一位 owner 管开始、结束和相关 API，其他工作读状态或离线数据。已有 watcher，就复用它，避免两份 collector 同时写结果、释放占用、调用统计。

网络超时也不表示远端未执行。重连后先看阶段身份、开始和结束记录；锁阻止第二轮进入，原产物说明第一轮走到哪里。

## 三、检查应该放在副作用之前

检查放在昂贵动作之前，才能真正减少重复成本。

改服务前核最终命令、来源、恢复对象；正式请求前检查模式入口；后处理前让新进程加载原配置。大部分可以在 CPU 完成。

AISBench 类在父进程能创建，配置经过生成、dump、reload 后，worker 却未必还能通过 registry 构建。后来检查新进程、真实构建入口，才覆盖到原失败点。只重复父进程构造，仍会漏掉它。

增加 N，还需核 collector 白名单、文件限制。只改 C，tokenizer、解析、统计都没动，就继承已有证明。

按本次变化限定范围：

| 本轮变化 | 应检查的主要边界 | 可以继承的事实 |
| --- | --- | --- |
| N、C、r | 实际参数、实体数量、受影响的采集边界 | 未变服务源码、tokenizer、观测逻辑 |
| AIS 扩展 | 配置生成、dump、fresh-process reload、受影响的 worker 路径 | 未变模型服务 |
| 服务源码或布局 | 最终运行身份、容量与相应服务验证、恢复对象 | 未变数据与计量定义 |
| 后处理环境 | 原数据绑定、子进程导入与原 selector | 已成功的正式推理 |

热参数点复用预热、路由验证；服务变化再做相应准备。重启后的预热长度、路由数量目前没有等效缩减证据，仍沿用原步骤。

## 四、数据与缓存决定这轮到底测了什么

128K/1K、约 90% 缓存涉及分词、Chat、页边界、路由。验收读取逐条 cached token，文本足够长本身不能保证命中。

本轮正文 131072，Chat 后 131076，输出固定 1024。每请求实际命中 118784，以 Chat 输入为分母得 90.6222%。初版页对齐预测还低于 90%，所以“约九成”和“每条至少九成”需要不同的检查。

DP 目标各有缓存，一条路由热了，不代表其他路由就绪。本轮先以独立 seed 准备，再逐路由 check，正式前的请求数、时间单独记录。

后缀跨轮重复也可能多命中。高缓存要防额外复用冒充参数收益，零缓存则需要对应的唯一性、状态控制。

报告一起保留正文、Chat、实际输出、命中范围、分母。名义输入吞吐表示承载量，新增计算量则另看非命中。

## 五、结果记录要允许“未知”，也要保留统计区间

最早的报告漏了 ITL，我追问后才补上。成功数、时延、吞吐窗口、接受计数应该一次交齐，而非每问一项再回头找。

TPOT 把耗时摊到输出，ITL 记录输出事件间隔。投机多 Token 提交、缓冲、传输会改变到达节奏，所以两者可能相差很大，Draft / Verify 设备时间则另量相应阶段。

128K C90 whole AL 为 `655360 / 113463 = 5.7760`，分子输出数、分母 Verify 次数。首 Token、额外 Token、结束截断都在这份计数中。

Compact 有 Verify cap 槽位计数，缺完整实际 proposal 数，严格接受率就保留 `NOT_OBSERVED`。AL 分母具备，并不补齐另一个指标的分母。

接受计数属于原窗口，native 则另存请求集、时段，244.86 才能追到具体样本、时长、卡数。

同轮 C90 为 P8+D8、16 卡、实体 N640、r6、逐条命中 90.6222%、输出 1024：

| 指标 | whole | AISBench native |
| --- | ---: | ---: |
| 纳入请求数 | 640 | 549 |
| 时间（s） | 179.5766 | 143.4935 |
| 平均系统并发 | 82.8179 | 87.4978 |
| 平均 TPOT（ms） | 10.3 | 10.4 |
| 输出吞吐（tok/s/PD16 卡） | 228.0921 | 244.8612 |
| AL | 5.7760 | 未单独采集 |

native 满足项目样本、时长要求；AL 仅在 whole 采集，表里按实际覆盖范围填写。原值见[结果摘录](../../assets/inference-tuning-workflow-postmortem/measurements.csv)。

## 六、失败以后，沿已经完成的阶段恢复

恢复先分清失败位置。

配置、导入在连接模型前失败，请求数为零，修入口再准备。服务已热、入口却不认本轮模式，就保留热状态，只补入口。两种情况都没有性能负例可记录。

推理后采集失败，先独立核原客户端、服务状态，再修原数据处理。开头那次保留了原错误，补 payload 搜索路径后继续用原 AIS 算法，计时、模型请求都没改变。

start/end、统计 API 状态未知时，owner 保留，先查进程、文件和完成证据。再次 start 可能重置状态，dump 也可能有副作用，不能直接重放。

回滚对象在候选开始前保存。源码、布局、场景会演进，默认脚本可能落后。性能负向先留结果，再按后续安排切回明确的父状态。

每次接续未完成阶段，已有工作才会累积。下一负载开始之前，先把原负载状态确认清楚。

## 七、跨会话继续，靠短入口和可靠产物

数天实验跨上下文，旧 RUNNING、PID、待完成事项容易被带入新一轮。全历史越多，查当前事实反而越费力。

短入口只留当前授权、场景、父身份、owner、已完成阶段、下一动作。实验、失败、日志各自存档，需要时按索引打开。

摘要负责阅读，结束文件、统计、变更回执提供证据。修好后处理，就更新当前结果、保留旧错误，过期 PENDING 不再覆盖已成功状态。

进度直接说所处阶段：尚未发请求、模型加载、正式请求执行、推理结束但采集失败。故障还要说明设备是否占用、重试是否可能重复请求，用户才知道剩下什么。

当前薄适配器仍有硬编码，执行、记录、汇总还需要收敛到共享入口。下一次纯 C 变更能否直接热测、零新增加载、一次交齐报告，可以检验这次整理是否有效。

负载结束、结果提取、足以决定是否保留，分别核对。有时前两项已经完成，只缺接受分母或确认窗口，就补那一项证据。

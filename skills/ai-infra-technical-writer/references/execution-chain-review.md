# 执行链文章的工程核验与图示分工

这些检查用于执行链或后端专题，不是每篇文章的固定目录。按题目承诺选择深度，沿同一请求连续解释；具体符号、分支和算子均须从目标版本取证。本文件的机制描述是核验问题，不是已验证的当前源码结论。

## 按标题验收代表路径

标题承诺“执行链路”时，选定相互兼容的版本、模型、后端及执行模式，核对一条实际可达的代表路径。沿调用方、构造位置、被调方和分支条件连接模型入口、具体模型层、后端分发与算子入口；无需穷举全部模型或优化分支。不能把分别真实却不可连通的符号拼成调用链，也不能用通用 Transformer 数学填补具体模型调用的证据断点。

标题承诺“跑到 GPU/NPU”时，解释与主线有关的输入 ID、positions、长度、缓存位置等在哪里构造、位于 CPU 还是设备、何时转换或传递。区分主机提交、设备完成、结果被消费三个时点；只在证据支持时写明同步与等待，不假设所有调用均同步或每轮都要同步。选定直接执行或图回放主线，再简洁说明另一模式的必要差异。追到算子入口可满足相应范围的源码文章，不机械要求 profiler 或底层闭源 kernel；若标题承诺实测轨迹，则必须有运行证据。

用同一请求贯穿相关的前缀命中、待算后缀、batch 输入、位置与 KV 映射、首 token 和后续 Decode。每次出现例子都应解释一项新的状态变化；检查索引、长度、shape 和时间顺序相容。主线先给读者能理解的分支描述，密集的模型或优化条件用邻近短表说明，不删掉决定路径可达性的条件。

交付前逐项回答标题验收问题。遇到断点先补证据与衔接，确实无法核实时明确缺口；不能未经用户同意把指定模型换成容易讲的模型，或靠缩小标题掩盖未完成的要求。

## 用时间线和布局转换检验连贯性

沿请求发生顺序检查跨章依赖：读者首次使用某个结果前，应已知道它从何产生。例如先交代 Prefill 的 logits 如何采样成首 token，再解释 Decode 如何消费它；后文只展开新的返回或状态变化，不倒回重教生成起点。允许有明确目的的回溯，但不能靠后章补齐前章成立所需的前提。

当标题同时覆盖多个阶段时，检查各阶段是否都有输入、状态读写、实际分发或算子入口、输出去向。篇幅可以不对称，关键边界不能空缺；不要将一个阶段追到算子，另一个仅画箭头直达结果。局部阶段专题不强制补齐其他阶段。

数学 shape、引擎打包布局和算子接口布局之间，用同一批 token 说明 reshape/切片、序列边界和长度含义。特别区分新增查询长度、有效 KV 长度与缓存池容量。同时核查投影结果到算子入口之间的 padding、有效 head 数与物理 head 数、返回后的切片，不能把局部数学 shape 直接当作实参 shape。教学维度可能不满足实际算子的 head_dim、对齐或页大小约束；用符号维度接回接口，并核对所选配置可达，不能让小数字例子隐含证明算子可运行。

## 先区分四种关系

区分进程/线程归属、函数调用、请求/张量数据流、设备执行时间。进程是执行边界，Rank 是并行身份，不用“进程或 Rank”作为同一类容器。图中箭头注明消息传递、构造/转换、调用或数据依赖，不能将对象演进图叫作真实调用栈。Scheduler 所在进程不等于“只做 CPU 工作”，Worker 也不自动意味着独立进程。

沿 batch 构造追到真实转换位置。若存在 ModelWorkerBatch 等中间结构，说明其职责或注明省略，不能凭记忆硬插，也不能把 ScheduleBatch → ForwardBatch 的教学缩写当直接调用。区分模型 forward 产出与运行时采样；设备执行栈是模型算子执行的展开，不能画成 Transformer 和 Sampling 完成以后才进入 NPU 的下一阶段。

## 调度与缓存必须改变主线中的行为

覆盖完整请求生命周期时，将调度器解释为持续事件循环：接收请求、更新状态、选批、提交执行、处理结果、输出及结束/资源处理。此处是职责顺序示意，函数名和调用次序按源码确认；输出可能在结果处理中，重叠调度可能处理上一批结果，不虚构一条同步循环。

用同一个请求说明 waiting 如何进入 batch、Prefill 后如何继续 Decode、停止条件如何生效。终止后的资源释放与可复用前缀保留需要区分。仅解释与主线有关的预算/容量约束，不扩成调度算法百科。

SGLang 前缀复用专题需追清 prefix match → 可复用 KV 索引与命中长度 → 根据命中长度确定待算后缀 → 本轮分配/映射 → Attention 读取。用 prompt [A B C D E F]、可复用 [A B C D]、新计算 [E F] 这类小例子解释 Extend，并注明假设缓存有效且符合目标布局/粒度。区分 Radix 索引与实际 KV 存储；命中不等于所有计算均被跳过。完整前缀命中、分页对齐、chunked prefill 等边界按目标代码解释，不推断“零 token forward 就能生成”。不同模型缓存结构、关闭缓存及其他缓存实现不强套标准 Radix/MHA 叙事。

## 硬件专题追到可确认的入口

题目明确承诺 Ascend 执行时，在可访问证据内至少展开一条代表性热点路径：配置/注册选择 → 模型层调用 → backend 分支 → 实际 operator 入口，说明输入、metadata/KV 使用与适用阶段。能确认时再深入一至两层；无法取得实现就明确停止边界，不用泛化硬件堆栈冒充已追到 kernel。

核对用户选择的模型与 backend，不把通用 ascend 后端当成所有模型唯一入口；例如用户参数是 dsv4 时，不未经检查改写成 ascend。标准 MHA 的 Q/K/V、KV 布局与算子不得直接当作特定 DeepSeek 模型实现。

区分普通 PyTorch 运算的设备分发、torch_npu 扩展、自定义算子、Ascend C/Triton 实现及运行时提交。它们可能交叉使用，不能未经核验画成互斥管线，也不能把库导入成功当成该请求调用了库内某个算子的证据。Prefill/Decode 的算子选择、metadata、KV 读写差异只讲已确认部分。图回放时区分捕获阶段与回放阶段，不暗示每轮必定逐层执行同样 Python 调用。

## 用不同视角的图解决不同问题

| 读者疑问 | 合适的表达 | 校验点 |
|---|---|---|
| 模块属于哪个进程、怎样传消息？ | 进程架构图 | 进程边界、消息方向、配置依赖 |
| 请求在边界上如何变形？ | 对象演进图或表格 | 所有者、构造位置、输入输出、中间结构 |
| 一轮计算如何读写张量？ | Forward 数据流图 | shape、KV 侧向读写、模型与采样边界 |
| Prefill 和多轮 Decode 何时发生？ | 时序图 | 首 token 来源、重复循环、异步边界、结束 |

端到端执行链文章优先加入时序视角；按目标界面把参与者控制在五个以内，必要时拆成服务侧与设备侧两图，并明确合并了哪些角色。不是强制凑齐四图。删除回答同一个问题且没有增加信息的全链图，不制作数屏高的总结巨图。

正常自回归教学时序中，首枚输出 token 可由 Prefill logits 采样；后续 Decode 消费前次生成 token。明确这是教学模式，投机与 chunked/mixed 模式另作条件说明。token 不等于汉字，也不保证每 token 一条 SSE 消息；流式输出可能受到分词解码、缓冲、输出间隔、停止字符串和结构化处理影响。

## 更换模型案例时重新核验受影响路径

用户要求从一种模型换成另一种时，先列出与模型绑定的断言：配置与类名、层内数据流、残差机制、Attention 与专家结构、缓存内容和布局、算子分发、生成或投机模式。保留已核实的通用请求主线，重新取证并改写受影响的正文、图、shape 表和来源，最后搜索旧模型名及旧机制残留；仅替换名称不构成更新。

默认 DeepSeek 案例可以选可核验的公开实现，但必须写清具体版本。公开主线与用户部署镜像分别建证据边界，不能用公开存在的同名后端推定容器内调用一致；也不要因某代 DeepSeek 使用压缩注意力，就机械套用另一代的 MLA 公式或缓存池。若选普通自回归主线，说明启用投机后的输入数量、验证和接受边界，不把普通 Decode 的单 token 时序冒充部署配置。

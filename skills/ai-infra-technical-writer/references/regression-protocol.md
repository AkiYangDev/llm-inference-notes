# 回归评测流程

1. 固定技能版本、任务输入和原始材料；每轮仅修改已证实的问题，默认最多三轮。
2. cases.json 为公开开发回归集。运行时仅向执行者提供 input、技能和必要原始材料，不提供 acceptance、旧输出或修复诊断。新任务再作为独立保留集，避免只适配已知题目。
3. 保存实际输出后再用 acceptance 判定 pass / fail / blocked / not_run，附判断证据。事实编造、版本偷换和虚构执行结果属于阻断失败，不能用文风分数抵消。
4. 条件允许时在相同任务与工具边界下对比旧版/新版；没有旧版行为输出就不能声称量化提升。结构校验、行为试用、真实硬件执行分别报告。
5. 记录问题ID、输入、失败输出、修改文件、复测输出及剩余风险。最终修改后复测受影响用例，不为凑通过率删除失败项或放宽验收。
6. 保存前检查范围内外差异，保留他人改动；校验来源许可和现有引用。只报告实际运行的样本数量，不把用例总数当通过数。

建议运行记录字段：skill_version、case_id、input、output、status、judge_evidence、tool_scope、limitations。输出和日志存于任务工作目录或已授权的持久化位置，不让下次独立试用读取历史答案。

完整成稿用例同时核对任务交付要求与技术验收；分别记录技术结论、篇幅/格式和可读性结果。声明计数字段及范围，不把混有代码的总字符数冒充中文字数。技术判读通过但交付条件未满足时，不报告整例通过。

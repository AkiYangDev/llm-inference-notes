# 源码链路与部署文章的证据要求

## 源码文章：沿真实边界解释对象变化

先锁定用户要讲的仓库、分支/commit、框架版本、模型变体、硬件和后端。有本地源码就读取实际文件与调用方；没有源码时查对应版本官方仓库及文档。记录查到的版本与关键来源。源码解析正文开头简洁注明已核实的仓库、commit SHA（或可确定的版本）、模型/后端与检索日期；检索日期不等于源码版本。关键引用优先固定到真实 commit 的文件及 symbol，必要时附已核实的行号。只能取得 main 时明确其可变性，不伪造固定版本。用户镜像或私有分支不可访问时，将公开源码说明与目标环境判断分开；正文用版本与适用范围表达这种边界，不反复叙述作者的访问过程。若目标环境就是题目要回答的问题，须明确该环境的结论尚未确认，不能仅将其排除后声称完成。不要以最新主线替代用户使用的厂内或旧版本分支，也不要声称阅读过不可访问的代码。

在起草实现细节前，找到与文章主题相关的真实 entry point、class、function、data structure 和 call path；沿调用方、被调方和数据构造位置交叉确认，而不是只搜索到同名符号就认定运行路径。检查版本、配置开关、后端选择、注册/分发逻辑与进程边界，确认该路径实际可达。内部保留简短的“关键断言 → 版本/配置 → 源码位置 → 辅助证据”记录；不必把研究记录整份塞入文章。

按目标版本源码、测试、官方文档、PR/issues、论文、第三方资料的顺序核实当前实现行为。测试可证明覆盖的预期与边界，但未执行测试不能说验证通过；PR 可能未合并，issue 可能只描述问题或建议，不能直接当已发布行为。资料与代码冲突时记录双方版本和条件，解释差异；若仍无法解释，只陈述能证明的范围。

证据排序不能跨问题类型滥用：算法定义和推导查原始论文，公开 API 承诺查对应版本文档，实际执行行为查目标代码，设计动机查作者说明或设计文档。仅从代码推导出的好处写作“可以推测/从工程效果看”，不能写成作者确定的设计理由。引用必须真实存在且直接支持相邻断言；不得编造 URL、标题、作者、commit、行号或所谓官方结论。

把 request → scheduler → batch → model runner → model forward → operator → backend/runtime → device kernel 当作追踪问题的导航，不是所有框架都必须符合的类名或直接调用关系。沿真实调用边、进程间消息、队列、回调、异步执行路径取证，保留影响理解的 tokenizer、采样、detokenization 和流式返回边界。证据只覆盖算子入口时，将分析范围明确限定到入口及其参数；不要延伸成具体设备 kernel 或运行轨迹的结论。

每经过一个与主题有关的边界，在正文中自然解释：为什么存在这一层，输入和输出是什么，对象或数据结构怎样变化，Tensor 的 shape/dtype/device 是否变化，是否通信或同步，属于控制面还是执行面。不是每层都硬塞七个小标题；不适用的检查略过，未确认的写明。

展示必要而短的代码，并提供真实路径和定位方式。省略代码应标注，伪代码要标“概念示意”，不可伪装成源文件摘录。图上的调用边必须与核实代码一致；进程边界与函数调用用清楚的标签区分。

不要把 ScheduleBatch、ForwardBatch、ModelRunner 各拆成一个名词解释章节。用一次 batch 的生命周期把它们联系起来，并按对应版本解释拥有者、职责、构造和传递位置。

与源文件或官方资料相邻地提供关键来源；不要给每句稳定概念塞引用，避免破坏叙事。对于不确定的具体实现，优先查证、删去或降低断言，不用免责声明包裹未经验证的细节。

## 部署文章：做到读者知道在哪执行、怎样验证

开头说明这篇实践解决什么问题、已经验证到哪一步，以及环境范围。集中交代物理节点、容器或宿主机、设备型号与数量、驱动/运行时、镜像、框架版本、模型名称和量化变体。未知字段标为未知，不从模型名猜兼容性。

按准备环境 → 检查设备与模型 → 启动 → 验证 → 排障的操作主线融入 5～7 个完整章节，不为每个参数单独开章。按复杂度选择进程、节点、端口、设备拓扑或启动链路图；仅保留能解决读者疑惑的图。

命令要求：

- 标明执行位置：哪个节点、宿主机或容器、工作目录、用户权限。
- 给完整可复制代码块，不夹杂 shell 提示符、解释性省略号或与命令混在一起的输出。
- 路径、模型目录、端口、监听地址和日志输出位置明确；参数解释紧邻命令。
- 真实环境值已知就使用已知值；未知时用集中变量和明显占位符，清楚说明必须替换的项，不声称模板可不经修改直接运行。
- 只使用已核实版本支持的 CLI 参数与环境变量；说明影响正确性、内存或通信的关键参数组合。
- 保留必要的环境初始化和多机各节点差异，不能为了简洁漏掉能决定成功与否的步骤。
- 不擅自升级软件、删容器、清进程、改线上配置或执行实际部署；写文章的请求不等于授权操作运行环境。

验证应覆盖有意义的阶段：设备可见与依赖正常、进程和监听端口、服务健康、模型可用、实际推理请求及响应。模型列表接口成功并不证明推理成功，进程存在也不证明初始化完成。流式、多机和投机推理按本文声称达到的范围补验证；没有执行的写成“验证方法/预期现象”，不写成实测结果。

排障围绕症状组织，例如启动阶段失败、端口拒绝、模型加载失败、内存不足或通信超时。把检查命令、日志位置和判断依据放在一起；不要把不同阶段的异常都归结为同一个参数。性能数据需说明硬件、版本、模型、输入输出长度、并发、预热、指标口径与测量方法；没有数据就不编数字。

结束时串起节点、进程、请求与设备执行路径，交代已验证的运行结果及影响复现的剩余限制；没有实际部署证据时，只说明操作和验证方法，不写成成功实践。结尾不额外转入无关的学习辅导。

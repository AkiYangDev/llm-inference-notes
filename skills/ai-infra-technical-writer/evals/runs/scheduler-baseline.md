# 一个请求怎样分两轮完成 Prefill，再进入 Decode

一个请求包含五个输入项，每轮最多处理三个，它就需要两轮才能完成输入处理。但“两轮处理”并不意味着“两次生成输出”。在教学实现 toy-r1 中，第一轮只推进处理进度，第二轮完成 Prefill 并记录首个输出，第三轮才进入 Decode，消费这个输出并产生下一个输出。

本文只讨论给出的虚构 Python 实现。请求的 prompt 为 `["A", "B", "C", "D", "E"]`，每轮预算为 3，所有轮次依次完成。`A` 到 `E` 是输入代号，`y1`、`y2` 是测试驱动提供的模拟采样结果，不代表汉字，也不是实际模型预测。

理解这条执行链，需要同时跟踪两种进度：输入处理到了哪里，以及已经记录了多少输出。`processed` 保存已经作为模型输入处理的逻辑位置数量，`output` 保存已追加的输出，`done` 决定请求是否结束。初始状态是 `processed=0`、`output=[]`、`done=False`。

每轮先由 `plan` 根据当前状态生成三元组 `(mode, items, end)`，确定阶段、本轮输入和完成后的进度；计算这些输入后，再调用 `finish` 更新请求。`plan` 本身不推进 `processed`。可以把它理解为一次工作安排，只有本轮完成后，`finish` 才把进度写回同一个请求。`items` 中的多个元素也始终属于这一个请求，并不代表多个请求组成的批次。

完整过程如下，表中的状态均为本轮 `finish` 执行之后的值：

| 轮次 | 阶段 | 本轮输入 `items` | `processed` | `output` | `done` |
|---|---|---|---:|---|---|
| 初始 | 尚未执行 | — | 0 | `[]` | `False` |
| 1 | Prefill | `["A","B","C"]` | 3 | `[]` | `False` |
| 2 | Prefill | `["D","E"]` | 5 | `["y1"]` | `False` |
| 3 | Decode | `["y1"]` | 6 | `["y1","y2"]` | `True` |

第一轮规划时，`processed=0` 小于 prompt 长度 5，因此进入 Prefill 分支。结束位置为 `min(0+3, 5)=3`，切片 `prompt[0:3]` 取出 `A、B、C`。这里的 `end=3` 是切片右边界，也是本轮完成后已经处理的位置数量。

本轮计算完成后，测试驱动向 `finish` 传入 `"unused"`。函数先把 `processed` 更新为 3，然后检查：当前是 Prefill，而且 `end=3` 仍小于 prompt 长度 5，于是直接返回。追加输出的语句没有执行，`"unused"` 因而不会进入 `output`，`done` 也保持初始的 `False`。

这个提前返回决定了分块 Prefill 的输出行为：完成一块输入，可以只留下进度变化，而不记录新的输出。第一轮已经做完自己的工作，但请求的 prompt 还剩 `D、E`，生成过程尚未跨过完整输入的边界。

第二轮继续读取同一个请求，此时 `processed=3`。由于 `3<5`，仍然选择 Prefill；预算虽然是 3，剩余输入却只有两个，因此结束位置被限制为 `min(3+3, 5)=5`。本轮拿到的是 `prompt[3:5]`，即 `D、E`。预算是上限，并不要求每轮都填满三个输入项。

第二次调用 `finish` 时，传入的模拟结果为 `"y1"`。函数把进度更新到 5，此时提前返回所需的 `end < len(prompt)` 已不成立，执行继续向下，将 `"y1"` 追加到 `output`。由于输出数量只有 1，尚未达到 2，请求仍未结束。

因此，首个输出在最后一轮 Prefill 完成时就已经进入请求状态。它不需要额外等待一轮 Decode 才出现，同时也为下一轮提供了必要输入：Decode 分支会读取 `output[-1]`。在这里，`y1` 的产生先于它被消费，两轮之间通过同一个请求对象衔接。

第三轮规划时，`processed=5` 已不小于 prompt 长度，代码转入 Decode 分支。本轮输入为 `["y1"]`，结束进度为 `5+1=6`。虽然调用仍传入 `budget=3`，Decode 分支并未使用这个预算；它只选择最近一个输出作为本轮输入。

第三次 `finish` 接收 `"y2"`，先把 `processed` 更新为 6，再追加 `"y2"`。这时 `output` 包含两个结果，满足 `len(output) >= 2`，于是 `done=True`。如果再次调用 `plan`，最前面的结束检查会直接返回 `None`，不会安排下一轮。

最终，`processed=6` 与两个输出并不矛盾：作为模型输入处理的是五个 prompt 项和 `y1`，而 `y2` 刚被记录，尚未作为下一轮输入。请求已经达到停止条件，所以无需继续消费它。这也说明，处理位置数与输出数量各有含义，不能互相替代。

toy-r2 草稿提出每个 Prefill chunk 都对外产生输出，但该提议尚未进入 toy-r1。当前实现能够确认的是请求内部列表的变化；材料没有网络返回代码，也没有真实 KV Tensor 或设备执行细节。沿着这一个请求，预算把五项输入切成两轮，最后一轮 Prefill 记录首个输出，Decode 再消费它生成第二个输出，最终由输出数量触发结束。

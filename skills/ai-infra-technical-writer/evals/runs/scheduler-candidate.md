# 一个请求怎样分两轮完成 Prefill，再进入 Decode

一个请求不必在一轮里处理完整个 prompt。在教学实现 toy-r1 中，请求带着五个输入代号 `A、B、C、D、E`，每轮 Prefill 的预算是 3，因此需要先处理前三个，再处理剩余两个。第二轮结束时记录第一个输出 `y1`，第三轮以 `y1` 为输入执行 Decode，记录 `y2` 后结束。理解这条执行线，需要始终分清：本轮处理了什么输入，以及本轮结束后追加了什么输出。

本文只讨论给出的虚构 Python 实现。`y1`、`y2` 是测试驱动传入的模拟采样结果，代码没有模型预测、真实 KV Tensor 或网络返回过程。另一份草稿 toy-r2 提议每个 Prefill chunk 都产生输出，但这项提议尚未进入 toy-r1，不能用来解释这里的行为。

请求的进度保存在同一个 `Request` 对象里。`prompt` 保存原始输入；`processed` 记录已经作为模型输入处理的逻辑位置数量；`output` 保存已经追加的输出代号；`done` 表示是否结束。初始时，后三者分别是 `0`、空列表和 `False`。可以把 `processed` 理解为输入处理游标，但进入 Decode 后，它仍会继续增长，并不永远受 prompt 长度限制。

每轮由 `plan` 读取状态，给出“模式、输入列表、完成后的游标”三项计划。计算该输入后，再由 `finish` 更新请求。`plan` 本身不会推进 `processed`；计划中的 `end` 只有在 `finish` 执行后才成为已完成进度。这和后端任务处理中“选出这一批工作”与“登记这一批已完成”的区别相似。本例只有一条请求，各轮依次完成，列表 `items` 始终属于它。

第一轮开始时，`processed=0`，小于 prompt 长度 5，因此选择 Prefill。预算为 3，终点是 `min(0+3, 5)=3`，切片 `prompt[0:3]` 得到 `A、B、C`。本轮计划就是 `("prefill", ["A", "B", "C"], 3)`。这里的三个元素是同一请求的三个输入位置，并非三条请求。

完成这段输入计算后，测试驱动把 `"unused"` 传给 `finish`。函数先把 `processed` 更新为 3，随后发现本轮属于 Prefill，且 `3<5`，于是直接返回，跳过追加输出和更新结束标记的代码。因此，第一轮虽然完成了三个输入位置，`output` 仍为空，`done` 仍为 `False`。`"unused"` 没有被记录，更不能解释成对外返回的第一个结果。

第二轮继续读取同一个请求。由于 `processed=3` 仍小于 5，模式仍是 Prefill。新的终点为 `min(3+3, 5)=5`，输入切片变成 `prompt[3:5]`，也就是 `D、E`。预算只是上限，剩余输入只有两个，所以本轮处理两个，不需要填满三个位置。

这一轮的 `finish` 收到 `"y1"`，先将 `processed` 更新为 5。此时 `end < len(prompt)` 不成立，函数不再提前返回，而是把 `y1` 追加到 `output`。输出数量为 1，尚未达到结束条件，`done` 保持 `False`。因此，第一个输出出现在最后一个 Prefill chunk 完成时；到这里，代码还没有执行过 Decode。它也没有从 `D、E` 推导出 `y1` 的逻辑，采样结果来自测试驱动。

把三轮放在一起，可以直接看到输入处理进度与输出数量并不同步。表中的状态均为该轮 `finish` 执行之后的值。

| 轮次 | 模式 | 本轮输入 | 传入的 sample | processed | output | done |
|---|---|---|---|---:|---|---|
| 1 | Prefill | `A、B、C` | `unused` | 3 | `[]` | False |
| 2 | Prefill | `D、E` | `y1` | 5 | `[y1]` | False |
| 3 | Decode | `y1` | `y2` | 6 | `[y1, y2]` | True |

第三轮开始时，prompt 已全部处理，`processed < len(prompt)` 为假，`plan` 转入 Decode 分支。它取 `output[-1]`，得到上一轮记录的 `y1`，并把完成后的游标设为 `processed+1=6`。这里可以访问最后一个输出，是因为第二轮已经追加了 `y1`。第三轮处理的是这个新输入，不会重新处理完整 prompt，也不会提前把尚未产生的 `y2` 当作输入。

本轮完成后，`finish` 把游标推进到 6，再追加传入的 `y2`。输出数量达到 2，`done` 随之变成 `True`。如果再次调用 `plan`，函数会在入口返回 `None`，不再安排工作。结束时，已处理的六个逻辑位置对应五个 prompt 位置加上 `y1`；`y2` 虽已进入输出列表，却没有作为下一轮模型输入被处理。

这条请求能分轮推进，依靠的是状态的连续传递：`processed` 决定还有哪段 prompt 待处理，最后一段 Prefill 为 Decode 留下 `y1`，Decode 再消费它并记录 `y2`，输出数量决定停止时机。分块边界因此不等于输出边界，产生一个输出也不等于已经处理了这个输出所对应的新输入位置。
